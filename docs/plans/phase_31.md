## 왜 이 일인가

Phase 29로 "백업에 문서 본문이 없다"를 고쳤다. 그 뒤 **전체 테이블을 열거해 대조**해 보니
백업이 덮는 건 19개 테이블 중 **6개**였다. 나머지 중 일부는 파생 데이터라 빼는 게 맞지만,
**사용자가 직접 만들었고 다시 만들려면 손이 가는 데이터**가 섞여 있다.

Phase 29와 같은 부류다 — 사용자는 "내 데이터 내보내기"를 눌렀으니 다 담겼다고 믿는다.

## 확인된 사실 (2026-07-26 마이그레이션·코드로 확인, 추측 아님)

전체 테이블 19개(`grep "create table public\." supabase/migrations/*.sql`).

### 백업에 이미 있는 것 (6)
`todos` · `memos` · `habits` · `habit_checks` · `calendar_events` · `pages`

### 빠져 있고, 사용자가 잃으면 아까운 것 (7)
| 테이블 | 무엇 | 잃으면 |
|---|---|---|
| **`feeds`** | 사용자가 등록한 RSS 피드(url·title·folder·status) | **직접 하나씩 다시 등록**해야 한다. 행이 작아 담는 비용이 거의 없다 |
| **`duck_state`** | xp·level·feed(먹이)·costume | 오리 레벨이 1로 돌아간다. **1행뿐이다** |
| `pomodoro_sessions` | 집중 기록(시간·태그) | 통계 이력이 사라진다 |
| `activity_daily` | github·claude_code 일일 활동 | github은 재수집 가능하지만 **claude_code는 로컬 수집기라 재수집이 어렵다** |
| `profiles` | 표시 이름·아바타(+ 대기 중 마이그레이션의 역할·기능 토글·대시보드 배치) | 이름·대시보드 배치가 초기화된다 |
| `page_versions` | 페이지 버전 히스토리 | 되돌리기 이력이 사라진다. **부피가 크다** — 담을지 판단 필요 |

### 별개 부류 — 브라우저에만 있는 데이터 (DB 아님)
`localStorage`에 있어 **계정을 옮기거나 브라우저를 바꾸면 그냥 사라진다.** 백업에도 없다.
- **할 일 순서**(id 배열) — Phase 21에서 "새 id면 순서가 끊긴다"고 이미 다뤘던 그 값이다
- 기사 북마크·읽음 표시(`bookmarkedArticles.ts` · `readArticles.ts`, 각 상한 200)
- 즐겨찾기(`favorites.ts`) · 온보딩 완료 여부

## Task

- **T1 — 값싸고 값 큰 둘부터: `feeds` + `duck_state`. ✅ 완료(2026-07-26)**
  - 형식 v2. **v1 파일은 계속 열린다** — 새 컬렉션을 선택으로 받아 없으면 빈 배열로 채운다.
    v1 하위호환 테스트 5건으로 잠갔다(오늘 내보낸 파일을 내일 우리가 거부하면 안 된다).
  - `duck_state`는 **insert만** 한다. upsert로 바꾸면 지금 레벨이 백업 시점으로 후퇴하는데,
    그건 "지금 데이터를 바꾸지 않는다" 계약 위반이다 — **upsert가 되는 순간 실패하는 테스트**를
    두었다(`captured.upsertCalled`).
  - `feeds`의 `fail_count`는 복원하지 않는다. 실패 횟수는 지금 이 계정에서 다시 세는 값이다.
  - 검증: core 50 + api 6 + web 신규 / turbo 18/18 GREEN.
  - 수용 기준: 내보낸 파일에 두 컬렉션이 담기고, 가져오면 복원된다. 라운드트립 테스트 통과.
  - `duck_state`는 user_id가 기본키라 **행이 1개**다. 복원은 "없으면 넣고 있으면 건드리지 않는다"
    (덮어쓰면 지금 레벨이 백업 시점으로 **후퇴**한다 — 가져오기의 "덮어쓰지 않는다" 계약과도 맞다).
  - `feeds`는 `(user_id, url)` 유일 제약이라 중복 복원이 그대로 멱등이다.
  - **형식 하위호환이 관건**: `parseBackup`은 지금 여섯 키를 **필수**로 본다. 새 키를 같은 방식으로
    필수화하면 **Phase 29가 내보낸 v1 파일을 우리 손으로 거부하게 된다.**
    → 새 컬렉션은 **없으면 빈 배열**로 받는다(선택). 그래야 옛 백업이 계속 열린다.
    → `formatVersion`은 2로 올리되 **1도 계속 읽는다**. 버전을 올리는 이유는 "이 파일에 무엇이
      들어 있는지" 구분하기 위해서지 옛 파일을 막기 위해서가 아니다.

  **계획이 적어 둔 "계층이 하나 늘어난다"는 사실이 아니었다.** 내보내기·가져오기는 **이미 전부

  **담은 8개** — 사용자가 손으로 정한 값: 할 일 순서 · 습관 순서 · 고정 메모 · 기사 북마크 ·
  즐겨찾기 · 접어 둔 카드 · 집중 태그 · 방해금지 시간.

  **일부러 뺀 것(근거를 테스트로 남겼다 — 다음 사람이 "빠뜨렸다"고 오해해 넣지 않도록)**
  - 테마 · 사이드바 접힘 — 기기별 취향이다. 밝은 사무실과 어두운 침실에 같은 테마를 강제하는 건
    개선이 아니다.
  - 읽음 표시 · 최근 페이지 · 최근 검색어 · 최근 이모지 — 파생값이라 쓰면 다시 쌓인다.
  - 오리 발화 카운터 · 알림 상한 · 주간 다이제스트 주차 — **복원하면 오히려 해롭다.**
    하루/주 단위 카운터를 백업 시점 값으로 되돌리면 상한 계산이 틀어진다.
  - 온보딩 완료 여부 — 새 브라우저에서 한 번 더 보는 게 손해가 아니다.

  **보안 성질**: 백업 파일은 외부에서 온다. **허용 목록으로 낯선 키를 버린다** — 없으면 남이 만든
  파일이 브라우저의 아무 키나 덮어쓸 수 있다. 다만 낯선 키가 있다고 **파일 전체를 거부하지는
  않는다**(그러면 멀쩡한 할 일·페이지까지 복원하지 못한다).

  - 복원은 **이미 있으면 건드리지 않는다**(Phase 29부터의 계약 그대로). 실제 사용 사례
    (브라우저를 바꿈)에서는 키가 없으므로 그대로 복원된다.
  - v1·v2·v3 파일은 계속 열린다. `localPrefs`가 깨져 있어도 **나머지 복원을 막지 않는다** —
    컬렉션과 달리 부가 설정이라 이것 하나로 데이터 복원을 통째로 막을 이유가 없다.
  - **한계(정직하게)**: 이건 기기 간 동기화가 아니다. 백업을 미리 받아 둬야 옮길 수 있다.
  - 검증: core 31 + web 9 신규 / turbo test·lint·build **18/18 GREEN**.
