# Phase 21 — 삭제 되돌리기 (파괴적 동작의 안전망 일관성)

착수 근거: `/loop-eng` SCOPE(5장). Phase 20 소진 → 신규 로드맵 발굴.

## 발굴 방식 — 프레임워크로 후보를 지어내기 전에, 코드가 스스로 드러낸 불일치를 봤다

5장은 marketing-skills(AARRR) 주도를 기본으로 한다. 그런데 이번 사이클에 `FEATURES.md` MUST
19건을 코드와 다시 대조하다가 **제품이 스스로 모순된 지점**을 발견했다. 추측이 아니라 관측이다.

- **페이지**는 삭제해도 안 지워진다. `is_trashed`/`trashed_at`(20260722030000_pages) + 휴지통
  화면(`TrashView.tsx`, `/pages/trash`) + 복원·영구삭제 API가 **이미 완성돼 있다.**
- **할 일·메모**는 삭제 버튼 한 번이면 **확인도 없고, 되돌릴 방법도 없고, 영구히 사라진다.**
  `handleDelete`가 곧바로 하드 삭제를 호출한다(`todos.ts:140`, `memos.ts:99`).

같은 제품 안에서 "페이지를 지우면 30일 보관, 메모를 지우면 즉시 소멸"이다. 사용자는 이 경계를
알 방법이 없고, 삭제 버튼은 hover로 나타나는 작은 아이콘이라 오클릭이 실제로 일어난다.
CLAUDE.md 5절이 "되돌리기 어려운 작업은 실행 전 확인"을 요구하는데 이 경로만 빠져 있다.

## 중복 방지 확인 (재구현 금지)

| 후보 | 코드 확인 결과 | 판정 |

| 습관 삭제 되돌리기 | 동일하게 없음(`habits.ts:95`) | T3 |

## 설계 결정 (ponytail 7단계)

- **할 일·메모까지 soft delete로 확장하지 않는다.** 테이블 2개 마이그레이션 + 모든 조회에 필터
  추가 + 타입별 휴지통 화면 + 보관기간 청소까지 따라온다. 조회 한 군데라도 필터를 빠뜨리면
  지운 항목이 검색·RAG에 되살아난다 — 얻는 것에 비해 표면이 너무 넓다.
- **되돌리기는 같은 id로 되살리는 방식**을 쓴다. 삭제 직전 행이 이미 클라이언트 메모리에 있고
  (`handleDelete`가 롤백용으로 들고 있다), Supabase insert는 id를 명시할 수 있다.
  → 삭제는 즉시 진짜로 일어나고(보류 상태 없음), 되돌리면 **id·생성시각까지 그대로** 돌아온다.
  - id를 보존해야 하는 이유: 할 일 순서는 localStorage에 id 배열로 저장되고(`ldd-todo-order`),
    RAG 임베딩도 sourceId로 묶인다. 새 id로 다시 만들면 순서가 흐트러지고 임베딩이 고아가 된다.
- **삭제를 지연시키는 방식은 버렸다.** "몇 초 뒤에 진짜 삭제"는 탭을 닫으면 삭제가 유실되고,
  `beforeunload`에서 비동기 요청을 흘려보내는 건 신뢰할 수 없다. 지금 삭제하고 되살리는 쪽이
  상태가 단순하다.
- **확인 다이얼로그는 넣지 않는다.** 되돌릴 수 있으면 매번 묻는 건 마찰만 늘린다(ConfirmDialog는
  영구삭제·전체삭제처럼 정말 못 되돌리는 자리에 이미 쓰이고 있다 — 그 경계를 흐리지 않는다).

## Task

### T1 계약 — 같은 id로 되살리기 (api, STDD)
- **수용 기준**:
  - `restoreTodo(supabase, todo)` / `restoreMemo(supabase, memo)` — 삭제된 행을 **id·created_at
    포함 그대로** 다시 넣는다.
  - 이미 같은 id가 존재하면(되돌리기 두 번 클릭 등) 에러가 아니라 **멱등 성공**으로 끝난다.
  - user_id는 인자로 받지 않고 현재 로그인 사용자로 채운다 — 남의 id를 실어 보내 남의
    데이터를 만들 수 없어야 한다(RLS가 막지만 계약에서도 막는다).
- **의존 계약**: 새 마이그레이션·새 스키마 없음. 기존 `todoSchema`/`memoSchema` 그대로.

### T2 배선 — 되돌리기 안내 (web)
- **수용 기준**:
  - 할 일·메모를 삭제하면 "삭제했습니다 · 되돌리기"가 잠시 뜨고, 누르면 같은 자리에 돌아온다.
  - 안내는 일정 시간 뒤 스스로 사라지고, 그 사이 다른 항목을 지우면 최신 것으로 교체된다.
  - 되돌리기 실패는 조용히 넘기지 않고 알린다(사용자가 복구됐다고 오해하면 안 된다).
  - 키보드로 도달·실행 가능하고 스크린리더가 안내를 읽는다(`role="status"`).
- **의존 계약**: 공용 컴포넌트 1개. 기존 위젯 2곳에서 사용.

### T3 습관 — 되돌리기가 아니라 삭제 전 확인으로 (착수 후 설계 변경)
착수 전 스키마 확인 결과 **되돌리기를 붙이면 안 되는 경우**로 판명됐다.
`habit_checks.habit_id`가 `on delete cascade`(20260721010100)라 습관을 지우면 **체크 기록이
전부 함께 사라진다.** 같은 id로 습관 행만 되살려도 스트릭은 빈 채로 돌아온다.

여기에 "되돌리기"를 달면 사용자는 복구됐다고 믿고 넘어가는데 실제로는 기록을 잃는다 —
안전망처럼 보이는 함정이다. 그래서 **되돌리기 대신 실행 전 확인**으로 바꾼다.
할 일·메모는 되돌릴 수 있으니 묻지 않고, 습관은 못 되돌리니 묻는다 — 경계가 분명해진다.

- **수용 기준**:
  - 습관 삭제를 누르면 **사라질 체크 기록 건수를 숫자로 밝히고** 확인을 받는다.
  - 취소하면 아무것도 지워지지 않는다.
  - 기존 `ConfirmDialog`를 쓴다(새 컴포넌트를 만들지 않는다).
- **대안 검토·기각**: 체크 기록까지 같이 되살리는 방안은, 위젯이 들고 있는 기간의 기록만
  복원돼 **오래된 기록이 조용히 잘린다**. 부분 복원을 완전 복원처럼 보이게 하는 건 더 나쁘다.
