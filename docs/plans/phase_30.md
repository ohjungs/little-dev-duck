## 왜 이 일인가

2026-07-26에 사용자가 화면을 직접 써 보고 30여 항목을 남겼다. 그중 22개는 같은 날 배포했고
(커밋 6건), **7개가 남았다.** 남은 것들은 전부 "작아서 미룬 것"이 아니라 **크거나 범위 합의가
필요해서** 미룬 것이다.

기록해 두는 이유가 두 가지 있다.

1. **다른 자동화가 이 저장소에 동시에 커밋하고 있다.** Phase 29(백업 이식성)를 진행 중인데
   이 피드백을 모른다. 아무 목록에도 없으면 남은 7개는 영영 안 잡힌다.
2. 이 저장소는 "MUST로 확정해 두고 안 한 것"을 Phase 20에서 코드 전수 대조로 겨우 찾아낸
   이력이 있다(`FEATURES.md` MUST 19건 중 반복 규칙 1건 누락). **적어두지 않으면 잊힌다.**

## Task

### T1 — 오리가 먼저 말을 건다 (피드백 1-3)

> "오리가 자율적으로 말을걸고 물어보고시키기 + 이미지랑 통합해서 자연스럽게 대화"

**수용 기준**
- 사용자가 아무것도 안 해도 오리가 상황에 맞는 말을 건넨다.
- 같은 상황에서 **하루에 정해진 횟수 이상 말하지 않는다**(테스트로 잠금).
- 방해금지 시간대에는 말하지 않는다.
- 무료 Gemini 쿼터를 자율 발화가 소모하지 않는다.

**설계 판단(착수 전 확정)**
- **말 걸 거리는 규칙으로 고른다, LLM으로 만들지 않는다.** "오늘 마감인 할 일 3건",
  "3일째 안 한 습관", "어제 커밋 0건" 같은 조건은 전부 결정적이다. LLM에 맡기면 무료 쿼터가
  잡담에 소모되고(Phase 19에서 이미 겪은 부류) 매번 다른 말이 나와 신뢰가 떨어진다.
  → core `duck-initiative.ts`(순수): 워크스페이스 상태 → 발화 후보 목록 + 우선순위.
- **인프라를 새로 만들지 않는다.** `quietHours`·`nextDailyCount`·`notify`가 이미 있다.
  재구현은 이 저장소 최고 심각도(CLAUDE.md 3-5절).
- **오리 상태 이미지와 묶는다**(사용자가 "이미지랑 통합"을 명시). 말풍선에
  `useDuckMood` 결과를 반영해 표정이 문장과 맞게 한다.

**하지 않을 것 (근거)**
- 서버 푸시·스케줄러: 무료 원칙상 서버 스케줄러가 없다(Phase 20에서 확정). 클라이언트가
  화면에 있을 때만 판단한다.
- 소리 알림: 요청에 없다.

**의존**: 없음. 즉시 착수 가능.

### T2 — 오리로 모든 기능 제어 + 작업 예약 (피드백 1-4)

> "할일 + 습관 + 뽀모도로 + 메모 + 캘린더 등 기존에 있는 모든 기능을 오리랑 대화하며
> 자연스럽게 작업예약이나, 기능을 사용가능했으면"

**지금 상태**: 도구 9종. **뽀모도로가 통째로 빠졌고, 수정·삭제가 없고, 예약이 없다.**

**수용 기준**
- 뽀모도로를 오리에게 말해서 시작·중지할 수 있다.
- 할 일·메모를 오리에게 말해서 **고치고 지울 수 있다.**
- "내일 아침에 ~하라고 알려줘" 같은 **미래 시점 예약**이 동작한다.
- 파괴적 도구(삭제·수정)는 **승인 카드를 반드시 거친다**(Phase 21 안전망 규칙).

**설계 판단**
- **삭제 도구는 되돌리기와 짝으로만 낸다.** Phase 19에서 "오삭제 위험"을 이유로 삭제 도구를
  의도적으로 탈락시킨 이력이 있다. 지금은 할 일·메모에 `restoreTodo`/`restoreMemo`와
  `UndoNotice`가 있으므로(Phase 21) 조건이 충족됐다 — **되돌릴 수 없는 대상에는 삭제 도구를
  만들지 않는다**(습관은 `habit_checks`가 cascade라 되살려도 기록이 빈다).
- **뽀모도로는 클라이언트 타이머다.** Phase 19에서 이 이유로 탈락시켰다. 서버 도구로는
  "시작 의도"만 기록하고 실제 타이머는 화면이 돌린다 — 도구가 직접 타이머를 만들 수 없다.
- **예약은 서버 스케줄러 없이 한다.** 무료 원칙. `calendar_events` + 클라이언트가 접속했을
  때 지난 예약을 확인하는 방식(주간 다이제스트 `WeeklyDigestTrigger`가 쓰는 것과 같은 패턴).
  → **한계를 사용자에게 명시한다**: 앱을 열지 않으면 알림이 늦는다.
- **도구가 늘면 라우터 입구를 함께 넓힌다.** 2026-07-26에 "도구를 만들고 승인 카드까지
  붙였는데 입구에서 막혀 한 번도 안 불린" 사고가 있었다(Phase 19 습관 체크). 도구마다
  트리거 문장을 `duckExamples.test.ts` 방식으로 **`routeUtterance`에 통과시켜 검사한다.**

**의존**: 없음. T1과 병렬 가능(다른 파일).

### T3 — 템플릿 마켓플레이스 (피드백 2-2)

> "실제 노션에 존재하는 모든 기능처럼, 템플릿을 선택 가능했으면 좋겠고,
> 마켓플레이스에서 가져올수있는 기능"

**수용 기준**
- 내장 12종 외에 **외부에서 템플릿을 가져올 수 있다.**
- 가져온 템플릿이 기존 페이지를 덮어쓰지 않는다.
- 신뢰할 수 없는 입력이 그대로 렌더되지 않는다.

**설계 판단**
- **"마켓플레이스"의 범위를 좁힌다.** 진짜 스토어(등록·검색·평점·결제)는 이 제품 규모에
  과하고 서버 인프라가 필요하다. 대신 **가져오기 경로 두 개**로 요구를 만족시킨다:
  1. **JSON 템플릿 파일 가져오기** — 내보내기의 역방향. 형식은 이미 있는 `PageTemplate` 타입.
  2. **내 페이지를 템플릿으로 저장** — 사용자가 만든 구조를 재사용(가장 자주 쓰는 형태).
- **보안이 핵심이다.** 외부 JSON이 BlockNote content로 들어간다. `dbSchema`는 zod로
  검증하고(이미 `createPage`가 한다), content는 **블록 타입 화이트리스트**로 거른다.
  Phase 24에서 확인한 원칙 — 외부 입력이 렌더에 닿는 지점은 검증·이스케이프.
- **원격 URL에서 직접 받지 않는다(1차).** SSRF·임의 콘텐츠 문제가 붙는다. 파일 업로드만.

**하지 않을 것**: 공개 템플릿 저장소 호스팅, 사용자 간 공유.

**의존**: 없음.

### T4 — 페이지 안의 엑셀 · 파워포인트 · 워드 (피드백 2-6) — **범위 합의 필요**

> "페이지 기능안에 그안에서 엑셀 + 파워포인트 + 워드 기능도 구현했으면 좋겠어"

**이게 왜 큰가**: 셋 다 "이미 있는 것의 개선"이 아니라 **신규 편집기**다.
관련 의존성이 저장소에 **0개**이고(xlsx·pptxgenjs·docx 전부 미설치), 셋을 다 만들면
이 제품에서 가장 큰 단일 기능이 된다.

**지금 있는 것과의 거리**

| 요구 | 지금 | 거리 |
|---|---|---|
| 워드(문서 서식) | BlockNote가 이미 제목·목록·표·이미지·코드블록을 한다 | **가장 가깝다.** 빠진 건 인쇄 레이아웃·페이지 나눔·글꼴/여백 |
| 엑셀(표 계산) | 데이터베이스 뷰(text·number·select·date + 필터·정렬·보드) | **수식·셀 참조·집계가 없다.** 데이터베이스는 "행=레코드"고 스프레드시트는 "셀=주소"라 모델이 다르다 |
| 파워포인트(슬라이드) | 없음 | **가장 멀다.** 고정 캔버스·슬라이드 순서·발표 모드가 전부 신규 |

**제안하는 단계(합의 대상)**

- **T4-a 워드부터** — 인쇄/PDF 레이아웃. 이미 `no-print` 클래스 관례가 있어 붙이기 쉽다.
- **T4-b 엑셀은 "수식 있는 표"로 좁힌다** — 데이터베이스에 `formula` 속성 타입 추가
  (`=SUM(가격)` 수준의 열 집계). 셀 주소(A1) 방식 스프레드시트는 **만들지 않는다** —
  기존 데이터베이스 모델과 충돌하고 사용자가 둘을 헷갈린다.
- **T4-c 파워포인트는 별도 Phase로** — 슬라이드는 블록 에디터가 아니라 고정 캔버스라
  BlockNote 위에 얹을 수 없다.

**착수 전 사용자 확인 필요**: 위 3단계 범위가 맞는지. 특히 **"엑셀"이 수식 있는 표를
뜻하는지, A1 주소 스프레드시트를 뜻하는지**에 따라 작업량이 몇 배 차이 난다.

**의존**: 사용자 답변.

### T5 — 좌상단 로고를 움직이는 오리 영상으로 (피드백 1-6) ✅ 완료(2026-07-26)

**한 일**: 사용자가 준 `duck-idle.mp4`를 **그대로 쓰지 않았다.** 로고는 24px인데 원본은
1280x720이라, 브라우저가 24px을 그리려고 720p 프레임을 **모든 앱 화면에서 상시** 디코딩한다.
같은 영상의 가운데를 정사각으로 잘라 96px로 줄인 파일을 만들어 쓴다(311KB → **24.8KB**).
외형은 원본 그대로고 해상도만 로고 크기에 맞췄다 — 오리 그림 자체는 손대지 않았다.
계획이 "성능을 먼저 확인한다"고 한 지점이며, 재고 나서 파일을 나눈 결과다.

- 펼친/접힌 사이드바 두 자리 모두 교체. 영상을 못 받으면 기존 SVG 로고로 떨어진다
  (로고가 사라지면 상단 좌측이 그냥 뚫려 보인다) — `DuckVideo`에 `fallback` 추가.
- 움직임 줄이기 설정은 `DuckVideo`가 이미 지킨다(재생 안 함 + 영상을 내려받지도 않음).
- **되돌아가면 실패하는 테스트**를 뒀다: 로고가 랜딩용 720p 원본을 쓰면 실패, 반복 재생이
  아니면 실패("계속 움직이는것처럼"이 요구였다), 파일이 원본의 1/4보다 크면 실패.
- **[사용자 확인]** 실제 렌더는 로그인이 필요해 못 봤다 — manual-verification 28번.


> "왼쪽위 작은오리 이미지는 내가 준 움직이는 오리 영상으로 대체해서 계속 움직이는것처럼해줘"

**수용 기준**
- 사이드바 좌상단 로고가 `duck-idle.mp4`로 계속 움직인다.
- 접힌 사이드바에서도 동작한다.
- **움직임 줄이기 설정을 켠 사용자에게는 재생하지 않는다**(현재 `DuckLogo`가 지키는 규칙).

**설계 판단**
- **자산·컴포넌트가 이미 있다.** `duck-idle.mp4` + `DuckVideo` + `lib/duckVideo.ts` 배치 계약.
  새로 만들 것은 32px 크기용 spec 하나뿐이다.
- **성능을 먼저 확인한다.** 이 영상은 지금 `/welcome`에서 `preload="none"` + poster로
  쓰인다(2026-07-26 실측 기록). 로고는 **모든 앱 화면에 상시 노출**이라 조건이 다르다 —
  자동재생 루프가 배터리·CPU에 주는 영향을 재고 나서 붙인다. 나쁘면 poster + hover 재생.

### T6 — 설정 화면 통합 + 프로필 편집 위치 교정 (피드백 6-1)

> "내가말한 모든것들은 설정에서 제어가능해야하고 기능추가설정 이런것도 있으면좋겠고"

**수용 기준**
- 이번에 만든 제어(대시보드 카드 구성·프로필 편집)를 **설정에서** 찾을 수 있다.
- 설정과 관리자의 경계가 한 문장으로 설명된다.

**설계 판단**
- **경계 규칙을 정한다**: 설정 = 내 것(개인화), 관리자 = 남의 것(권한 부여).
  이 기준이면 **프로필 편집·대시보드 구성은 설정으로 가야 한다.** 지금 관리자에 있다(위 별건).
- **읽기 전용 프로필 카드를 편집 가능하게 바꾼다** — 새 카드를 추가하지 않는다.
  같은 것이 두 곳에 생기면 어느 쪽이 진짜인지 알 수 없다.
- 설정 카드가 13개라 이미 길다. **묶음(개인화 / 연동 / 데이터 / 위험)으로 접는다.**

**의존**: 없음. 작다.
