# Phase 36 — 서버 인스턴스 메모리에 기대는 자리 정리

> 상태: **draft(예약·미착수)** — 2026-07-26 `/loop-eng` 자체 리뷰에서 부류를 발견해 작성.
> 착수 직전 **stale 가드 필수**: 아래 목록을 다시 세고 시작한다.

## 왜 이 일인가

2026-07-26 자체 리뷰에서 **같은 결함을 두 곳에서** 찾았다 — `Map`에 넣기만 하고 지우지 않아
항목이 영원히 남는 것(계정 삭제 호출 기록 · GitHub 잔디 캐시). 둘 다 그 자리에서 고쳤다.

고치면서 드러난 **더 큰 사실**이 이 Phase의 근거다:

> 이 앱의 호출 상한·캐시는 전부 **서버 인스턴스 메모리**에 산다.
> Vercel은 인스턴스를 여러 개 띄우고 수시로 재활용한다 — **상한은 인스턴스 수만큼 느슨해지고,
> 캐시는 인스턴스가 바뀌면 사라진다.**

`PENDING.md` 6번이 이미 같은 말을 하고 있다("그 상한은 서버 인스턴스 메모리 기반이라
인스턴스가 여럿이면 느슨해집니다"). 즉 **알고는 있는데 어디에 몇 개나 있는지는 아무도 세지 않았다.**

## 확인된 사실 (2026-07-26 코드로 확인)

| 자리 | 무엇 | 지금 문제 |
|---|---|---|
| `api/account/delete` | 30초 재호출 차단 | 인스턴스가 다르면 차단이 안 먹는다(되돌릴 수 없는 경로다) |
| `api/github/contributions` | 30분 캐시 | 인스턴스가 바뀌면 캐시 미스 → 공유 토큰의 요율을 더 먹는다 |
| `api/keepalive` | 시간당 호출 상한 | `PENDING.md` 6번이 이미 명시 — 완전한 차단은 `CRON_SECRET` |

**셋 다 지금 당장 고장은 아니다.** 개인 워크스페이스 규모에서는 인스턴스가 대개 하나고,
느슨해져도 피해가 작다. 그래서 **이 Phase는 급하지 않다** — 다만 "왜 이렇게 두었는지"가
코드에 없으면 다음 사람이 이걸 믿을 만한 상한으로 오해한다.

## Task (안)

- **T1 — 한계를 코드에 적는다(고치는 것보다 먼저).**
  - 세 자리 각각에 "인스턴스 메모리라 이만큼만 보장된다"를 한 줄로 남긴다.
  - 새 상한·캐시를 만들 때 같은 함정에 빠지지 않도록 한곳에서 참조할 수 있게 한다.
  - **이것만으로 이 Phase의 8할이 끝난다** — 나머지는 값이 애매하다.

- **T2 — 진짜 필요한 곳만 골라 옮길지 판단한다.**
  - 후보: 계정 삭제 차단(되돌릴 수 없어 유일하게 값이 크다).
  - **옮기려면 저장소가 필요하다**(DB 테이블 = 마이그레이션, 또는 외부 KV = 의존성·비용).
    둘 다 지금 무료 원칙·마이그레이션 적체와 충돌한다 → **기본은 "옮기지 않는다"**.
  - 옮기지 않기로 하면 그 근거를 남기고 T3으로 간다.

- **T3 — 확인 문구 게이트가 실질 방어임을 명시.**
  - 계정 삭제의 실제 안전망은 30초 차단이 아니라 **문구 타이핑**이다. 자동화된 반복 호출은
    문구를 모른다. 그 사실을 적어 두면 상한을 과신하지 않게 된다.

## 의존 계약

- **T1·T3은 주석·문서만.** 코드 동작 변경 0.
- T2는 판단이며, "옮긴다"로 결론나면 그때 마이그레이션 계획을 별도로 세운다.

## 하지 않을 것

- Redis·Upstash 같은 외부 KV 도입. 무료 원칙과 충돌하고, 지금 규모에서 얻을 게 없다.
- 인스턴스 메모리 상한을 **지우는 것**. 느슨해도 없는 것보다 낫다(같은 인스턴스의 연타는 막는다).
