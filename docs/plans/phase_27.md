## T1이 우선인 이유 — 이건 누락이 아니라 버그다

캘린더 위젯의 `formatEventTime`은 **자정이면 시각을 숨기도록** 짜여 있다
(`if (h === 0 && m === 0) return null` — "종일 일정은 시각을 보여주지 않는다"는 의도).

그런데 `handleAdd`가 날짜를 `new Date("2026-07-28").toISOString()`으로 만든다. 날짜만 있는
ISO 문자열은 **UTC로 해석**되므로 `2026-07-28T00:00:00.000Z`가 되고, 한국(UTC+9)에서
`getHours()`는 **9**다. 결과: **날짜만 고른 일정마다 "오전 9:00"이 붙는다.**
사용자는 시각을 고른 적이 없는데 화면은 9시라고 말한다.

**오리와도 어긋나 있다**: 오리의 `coerceEventStart`는 날짜만 받으면 `T00:00:00+09:00`
(KST 자정)로 만든다. 같은 앱 안에서 **캘린더에 일정을 넣는 두 경로가 서로 다른 시각**을
저장하고 있었다.

- **할 일 마감일과 규약이 다른 건 의도다.** 할 일은 화면이 `dueDate.slice(0, 10)` 문자열로
  오늘을 판정해서 **UTC 자정**이 맞고(Phase 23), 캘린더는 `getHours()`로 표시해서
  **로컬 자정**이 맞다. 읽는 방식이 다르니 저장 규약도 다르다 — 이 차이를 주석으로 남긴다.

## 중복 방지 확인 (코드로)

| 후보 | 확인 결과 | 판정 |
|---|---|---|
| 캘린더 종료 시각 계약 | `createCalendarEvent`가 `endAt`을 **이미 받는다** | 재구현 안 함 — 화면만 연결 |
| 종료 시각 표시 | `event.endAt ? formatEventTime(event.endAt) : null` 이미 있음 | 이미 있음 |
| 시작 시각 입력 | 추가 폼에 `type="time"` 0건 | **없음** → T2 |

## 설계 결정 (ponytail 7단계)

- **로컬 자정으로 저장한다.** `new Date(y, m-1, d)`로 만든다 — 문자열 파싱은 날짜만 있으면
  UTC로 해석되는 게 표준이라 그 함정을 피한다. 시간대를 하드코딩(`+09:00`)하지 않는다:
  화면이 `getHours()`(로컬)로 표시하므로 **저장도 로컬 기준이어야 짝이 맞는다.**
- **시각은 선택 입력이다.** 비우면 지금처럼 종일 일정(시각 표시 없음). 날짜만 넣던 흐름을
  깨지 않는다 — 대부분의 일정은 시각까지 필요하지 않다.
- **종료 시각은 시작 시각을 넣었을 때만 받는다.** 시작 없이 종료만 있는 일정은 의미가 없고,
  입력칸이 셋이면 폼이 무거워진다.
- **기존 데이터는 건드리지 않는다.** 이미 저장된 일정의 시각을 일괄 수정하는 건 되돌리기
  어려운 데이터 변경이라 하지 않는다. 새로 만드는 일정부터 바르게 저장된다.

## Task

### T1 날짜만 고른 일정에 없는 시각이 붙지 않게 (버그)
- **수용 기준**: 날짜만 골라 만든 일정은 화면에 시각이 표시되지 않는다.
  변환은 순수함수로 분리해 **어느 시간대에서 돌려도** 로컬 자정임을 테스트한다.

### T2 시작·종료 시각 입력 (누락)
- **수용 기준**:
  - 추가 폼에서 시작 시각을 선택할 수 있고, 넣으면 그 시각으로 저장·표시된다.
  - 시작 시각을 넣었을 때만 종료 시각을 넣을 수 있다.
  - 종료가 시작보다 이르면 저장하지 않고 알린다.
  - 비워 두면 종전대로 종일 일정.
- **의존 계약**: `createCalendarEvent`가 이미 `endAt`을 받는다. 스키마·마이그레이션 변경 없음.

## 별도 기록 — 코스튬(먹이 재화의 종착지)이 없다

`duck_state.costume` 컬럼과 "먹이(재화)" 개념이 있고, `balance.ts` 주석은 먹이를
**"코스튬 구매 재화"**라고 적고 있으며, DECISIONS.md는 "코스튬은 레벨 해금 + 먹이 구매
혼합"으로 **확정**해 뒀다. 그런데 `costume`은 **저장만 되고 어디에서도 읽히지 않는다** —
화면에 코스튬 선택도, 상점도 없다. 즉 XP를 쌓아 먹이를 모아도 **쓸 곳이 없다.**

**이번 Phase에서 만들지 않는다.** 오리는 픽셀 스프라이트 한 장(`ducky_2_spritesheet.png`)으로
그려지므로 코스튬에는 **새 그림이 필요**하고, 이 저장소의 오리 외형은 사용자가 직접 만들어
넣어 온 영역이다(스프라이트·영상 모두). 색조 필터 같은 걸로 임의 대체하면 사용자가 원치 않는
방향으로 제품 정체성을 바꾸는 셈이다. → `manual-verification.md`에 사용자 결정 항목으로 기록.
