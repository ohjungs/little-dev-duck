## 설계 판단 — 계획의 "formula 속성 타입"에서 한 칸 물러난다

Phase 30은 `formula` **속성 타입** 추가로 적었다. 그런데 그 괄호 안의 정의가 `=SUM(가격)`
**열 집계**다. 그렇다면 문자열 수식을 파싱할 이유가 없다.

| 안 | 필요한 것 | 판단 |
|---|---|---|
| (a) `formula` 속성 타입 + `=SUM(...)` 문자열 파싱 | 식 파서 · 순환 참조 검사 · 오류 표기 · 새 주입 표면 | **안 한다** — 미니 프로그래밍 언어다 |
| (b) 열마다 집계 종류를 고르고 표 아래 줄에 보여준다 | enum 하나 + 순수 계산 함수 | **한다** |

(b)가 같은 요구를 만족시키면서 파서가 없다. 노션의 "계산" 행도 이 형태다.
**사용자가 표에서 아쉬운 건 "합계가 안 보인다"이지 식을 쓰고 싶은 게 아니다.**

## 확인된 사실 (2026-07-26 코드로 확인, 추측 아님)

- 속성 타입 5종: `text` · `number` · `select` · `checkbox` · `date`
  (`database-view.ts:6`). **수식·셀 참조·집계 전부 없다.**
- 뷰 정의는 `pages.db_schema`(jsonb)에 산다 — `sort`·`filters`·`hiddenPropIds`가 전부
  **하위호환 기본값**으로 추가된 전례가 있다(`database-view.ts:108` 주석).
  → **마이그레이션 불필요.** 같은 방식으로 선택 필드를 하나 더 단다.
- 행 값 타입은 `string | number | boolean | null` (`rowPropValueSchema`).

## Task

- **T1 — core 집계 엔진(순수).**
  - 집계 종류: `none` · `count`(행 수) · `filled`/`empty`(채워진/빈 칸) · `sum` · `avg` ·
    `min` · `max` · `checked`(체크된 수).
  - 수용 기준: 숫자 아닌 값이 섞여도 터지지 않는다 · 빈 표에서 0/빈값을 올바로 낸다 ·
    타입에 맞지 않는 집계(예: text에 sum)는 **고를 수 없다**.
  - `viewDefSchema`에 `aggregations`를 **선택 필드**로 추가 — 없으면 `{}`.
    기존 db_schema가 그대로 열려야 한다(백업 v1 하위호환에서 배운 것과 같은 규칙).

- **T2 — 표 아래 집계 줄 + 고르는 UI.**
  - 표 뷰 하단에 열마다 집계 결과를 보여준다. 열 머리 메뉴에서 집계 종류를 고른다.
  - **`none`이 기본** — 모든 표에 갑자기 숫자가 생기면 안 된다.
  - 보드 뷰는 대상이 아니다(열 개념이 없다).

- **T3 — 인쇄에 함께 나가는지 확인.** T4-a가 만든 지면 규칙과 충돌하지 않아야 한다
  (집계 줄이 표와 분리돼 다음 장으로 넘어가면 안 된다).

## 의존 계약

- core `database-view.ts`: `AGGREGATIONS` enum + `viewDefSchema.aggregations`(선택) +
  `computeAggregation` 순수함수.
- **DB 마이그레이션 없음** — `db_schema` jsonb 안의 선택 필드.
- UI는 `DatabaseView.tsx`만 건드린다.

## 하지 않을 것

- A1 주소 스프레드시트 · 셀 간 참조 · 수식 문자열 파싱.
- 행 단위 계산 열(단가 × 수량). 요구된 것은 집계이고, 이건 파서를 다시 부른다.
  필요하다고 판명되면 그때 별도로 정한다.
