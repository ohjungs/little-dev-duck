## 1. 스코프 전제

### 1-1. 개인용 메신저의 근본 문제

[확인됨] 메신저 기능의 절반 이상은 "상대방의 존재"를 전제한다. 읽음 표시, 입력 중 표시, 그룹 권한, 차단, 신고는 상대가 없으면 코드는 돌아도 의미가 없다.

세 가지 성립 시나리오:

- S1. 싱글 유저: 나와의 채팅방만 존재. 사실상 채팅 UI를 쓴 저널 또는 인박스.
- S2. 나 + AI 오리 에이전트 다수: 오리, 비서 오리, 리뷰어 오리가 각각 발화 주체. 읽음, 입력 중, 그룹채팅이 전부 의미를 회복한다.
- S3. 소규모 실제 멀티 유저: 지인 5명 이내 초대.

이 카탈로그는 S2를 기본 축으로 하고, S3에서만 성립하는 항목은 별도 표기했다.

### 1-2. 무료 티어 실측 제약

[확인됨] Supabase Free (2026년 기준 공개 자료): DB 500MB, 파일 스토리지 1GB, 대역폭 5GB/월, MAU 5만, Realtime 동시 접속 200, Realtime 메시지 200만/월, 메시지 최대 256KB, 활성 프로젝트 2개, 7일 무활동 시 프로젝트 자동 일시정지, 백업 없음.

이 중 메신저에 치명적인 것은 두 개다.

1. 7일 무활동 자동 일시정지. 메신저는 "언제나 켜져 있다"가 전제인데 프리 플랜은 그 전제를 깬다. [확인됨]
2. 파일 스토리지 1GB. 사진과 음성을 주고받으면 수개월 내 소진된다. [추정] 원본 사진 3MB 기준 약 330장.

대응 방향은 3-V 섹션에 정리했다.

## 4. 최소 데이터 모델 스케치

[가정] 아래 스키마는 현재 확정된 문서가 없어 초안으로 제시한다. 확인 방법: 기존 LDD 마이그레이션 파일과 대조.

- profiles: id, display_name, avatar_url, status_message, last_seen_at
- rooms: id, type(direct, group, agent, self), title, created_by, created_at
- room_members: room_id, member_id, member_type(user, agent), role, joined_at, last_read_message_id, muted_until, pinned_at
- messages: id, room_id, sender_id, sender_type, client_msg_id(unique), seq, type, body, created_at, edited_at, deleted_at
- attachments: id, message_id, storage_path, mime, byte_size, width, height, thumb_path
- reactions: message_id, actor_id, emoji
- agents: id, name, persona_prompt, tool_scopes, enabled

핵심 제약 세 가지:
1. client_msg_id 유니크로 중복 전송 차단
2. seq는 서버가 부여 (클라이언트 시계 불신)
3. deleted_at 소프트 삭제 (하드 삭제는 정리 잡에서만)
