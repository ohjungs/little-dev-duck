## 1. OAuth 어댑터 기기 실기검증

- **Task**: Phase 10 — Google Calendar / GitHub 이슈 / Gmail 어댑터.
- **무엇을**: 로그인→provider_token 캡처→승인 카드→실제 외부 API 반영→감사 로그까지 end-to-end.
- **왜 사용자 필요**: 실제 OAuth 로그인 플로우·외부 계정 권한이 필요. 무인 세션은 브라우저 로그인 불가.
- **재현 절차**: 배포된 웹에서 Google/GitHub 로그인 → 설정에서 어댑터 연동 → 오리에게 "내일 회의 잡아줘"
  등 액션 요청 → 승인 카드 확인 → 실제 캘린더/이슈/메일에 반영됐는지 대조.
- **현재 상태**: Google Calendar는 2026-07-23 사용자 검증 통과(종결). GitHub 이슈·Gmail 어댑터는 코드 완료·미검증.

## 7. 정적 프리렌더 페이지의 CSP nonce 차단 — ✅ 해결됨 (2026-07-26, 사용자 "알아서 결정" 위임)

- **결정**: `/welcome`에 `export const dynamic = "force-dynamic"` 한 줄. 대안이던 "정적 공개 경로만
  CSP 완화"는 보안 미들웨어에 분기를 넣는 쪽이라 채택하지 않았다 — proxy.ts 주석대로 CSP는 과거에
  한 번 깨진 이력이 있는 민감 영역이고, 랜딩 트래픽 규모에서 per-request 렌더 비용은 무시할 수준이다.
- **검증**: CSP 콘솔 오류 **23건 → 0건**, 하이드레이션 `true`(desktop·mobile 양쪽), nonce 0개 → 1개.
  증거: `docs/loop-eng/screenshots/2026-07-26/phase18-csp-welcome/`.
- **부수 발견(같이 수정)**: CSP를 고쳐도 Analytics는 여전히 죽어 있었다. Vercel Analytics가 받아오는
  `/_vercel/insights/script.js`가 미들웨어 matcher에 걸려 **303으로 /welcome(HTML)을 돌려받고** 브라우저가
  "MIME type text/html is not executable"로 거부하고 있었다. matcher에 `_vercel` 제외를 추가해 해소
  (로컬은 플랫폼 파일이 없어 404가 정상, Vercel에서는 실제 스크립트가 서빙된다).
  → **랜딩 유입 지표를 막던 원인은 CSP와 matcher 2개였고 둘 다 수정됨.**

  동적 렌더 페이지에서만 지원한다고 명시.)

  소셜 카드는 배포된 공개 URL을 크롤러가 읽어야 확인 가능(로컬 불가).
- **재현 절차**: ① 페이지를 "웹에 공개" → 링크 복사 ② 시크릿 창으로 열어 읽기 전용 확인

  ④ https://cards-dev.twitter.com/validator 또는 슬랙 미리보기로 og:image 로딩 확인.
- **현재 상태**: 코드·빌드·메타데이터 검증 완료(og:image 200, 절대 URL 생성 확인). 실제 소셜 카드 육안 미검증.

## 9. OG 카드에 한글 제목 넣기 — 한글 폰트 자산 도입 결정 필요 (Phase 18 T1 축소분)

- **무엇을**: phase_18.md T1 수용 기준은 "OG 이미지에 페이지 제목"이었으나, 이번엔 **브랜드 카드**로만 구현.
- **왜 축소**: satori(next/og)는 글리프를 그리려면 폰트 버퍼가 필요한데 저장소에 한글 폰트가 없다
  (Geist=라틴 전용). 폰트 없이 한글 제목을 넣으면 전부 두부(□)로 깨진다.
- **왜 지금은 문제 아닌가**: 카톡·슬랙·X 모두 카드에서 **og:title을 텍스트로 따로 렌더**하므로 한글 제목은
  이미 사용자에게 보인다. 이미지 안 제목은 중복이다(ponytail).
- **결정 (2026-07-26, 사용자 "알아서 결정" 위임)**: **넣지 않는다. 브랜드 카드로 확정.**
  (a) Noto Sans KR 서브셋 TTF ~1.5MB 저장소 추가 — 이미 og:title로 보이는 텍스트를 이미지에 한 번 더
  그리자고 저장소에 1.5MB 바이너리와 라이선스 파일을 들이는 건 YAGNI.
  (b) 요청 시점 Google Fonts 글자 단위 서브셋 fetch — 외부 런타임 의존 + satori가 woff2를 못 읽어
  "구형 UA를 보내면 ttf를 준다"는 미문서화 동작에 기대야 한다. 카드가 조용히 깨질 경로를 만드는 셈.
  → 얻는 것(중복 텍스트)보다 잃는 것(용량·취약한 외부 의존)이 크다. 재검토 트리거: 사용자가 카드에
  제목이 없어 불편하다고 하거나, 저장소에 한글 폰트가 다른 이유로 이미 들어오는 경우.
- **현재 상태**: 브랜드 카드로 완료·검증됨(1200x630 PNG 정상 렌더 확인). **항목 종결.**

## 11. 오리 주간 다이제스트 실기 검증 (Phase 18 T4) — 로그인 + 시간 경과 필요

- **무엇을**: ① 앱에 들어갔을 때 지난 주 다이제스트 페이지가 자동으로 한 번 생성되는지
  (제목 `주간 다이제스트 2026-07-13 ~ 2026-07-19`, 본문에 할 일·습관·집중·페이지·일정 수치)
  ② 같은 주에 다시 들어가도 두 번 만들지 않는지 ③ 데스크톱 위젯과 브라우저를 같이 써도
  하나만 생기는지(서버 제목 중복 검사) ④ 알림이 방해금지 시간대엔 안 뜨는지.
- **왜 사용자 필요**: 로그인 뒤 워크스페이스 + 실제 활동 데이터 + **주 경계를 넘는 시간 경과**가
  필요하다. 로컬에 Supabase 자격증명이 없고, 시간 여행 없이 "다음 주에 다시 뜨는지"는 확인 불가.
- **재현 절차**: ① 앱 접속 → 페이지 목록에 다이제스트가 생겼는지 확인 ② 새로고침 → 하나만 있는지
  ③ 개발자도구에서 localStorage `ldd:weeklyDigest` 삭제 후 새로고침 → **서버 중복 검사가 걸려**
  또 생기지 않아야 정상 ④ 다음 주 월요일 이후 접속 → 새 다이제스트 생성.
- **자동 검증으로 잠근 것**: 주차 키 판정(중복·저장값 오염·시계 되돌림, core 13 tests), 본문 포맷

## 21. 데이터베이스 행 속성이 오리 답변에 반영되는지 (2026-07-26) — 로그인 필요

- **무엇을**: 데이터베이스 페이지(예: Phase 18 "프로젝트 트래커" 템플릿)에서 행의 속성값을
  채운 뒤, 오리에게 **"진행 중인 프로젝트 뭐 있어?"**처럼 **값 기반으로** 물었을 때 답하는지.
- **왜 사용자 필요**: 로그인 + Gemini 호출 + 실제 데이터가 있어야 확인된다.
- **무엇이 문제였나**: 행 속성값은 `row_props` 컬럼에 따로 저장되고 `plain_text`에는 들어가지
  않는다(plain_text는 본문에서만 파생). 그래서 **RAG 임베딩에 값이 아예 없었다** — 오리가
  상태·우선순위 같은 값을 볼 수 없었다. 제품 정의는 "오리는 RAG 기반으로 사용자의 데이터를
  알고 답한다"인데 그 데이터의 일부가 빠져 있던 셈.
- **어떻게 고쳤나**: 임베딩 텍스트를 `pageEmbedText(plainText, rowProps)`로 조립한다
  (저장 컬럼과 별개로 호출부에서 만드는 건 `todoEmbedText`가 이미 쓰던 방식).
  **`plain_text` 자체는 바꾸지 않았다** — 속성만 고칠 때도 다시 파생하려면 본문을 함께 알아야
  해서 편집마다 추가 조회가 붙는다.
- **기존 데이터는 자동 반영되지 않는다**: 페이지를 저장하거나 백필(`/api/ai/reindex-all`)이
  돌아야 새 임베딩이 만들어진다. 백필은 앱 최초 진입 시 1회 자동 실행된다.
- **알려진 한계**: **Cmd+K 검색은 여전히 속성값을 못 찾는다**(검색은 title·plain_text만 본다).
  검색까지 덮으려면 plain_text 파생을 DB 트리거로 옮기거나 편집마다 추가 조회가 필요해
  이번 범위에서 뺐다.
- **자동 검증으로 잠근 것**: 임베딩 텍스트 조립(본문만·속성만·둘 다·빈 값·숫자·불리언
  false 구분·입력 순서 유지) core 9 tests.
- **현재 상태**: 코드·타입·린트·빌드·테스트 GREEN. 실제 대화 검증 미실시.

## 22. (2026-07-26) 기존 데이터는 재인덱싱해야 날짜가 반영된다

- **무엇을**: 할 일 마감일·일정 시각이 RAG 임베딩에 들어가게 고쳤다(core embed-text.ts).

- **현재 상태**: 코드·테스트 통과. 실제 검색 품질은 실기 확인 필요.

## 23. (2026-07-26) 조회와 변경이 한 문장에 섞이면 조회 절반이 유실된다 [해결됨 2026-07-26]

  (`packages/api/src/agent.ts` — mutating이 하나라도 있으면 auto 호출은 버려진다).
- **왜 지금 안 고쳤나**: 조회 결과를 승인 대기 응답에 실으려면 계약(`DuckChatResponse`)과
  승인 카드 UI가 함께 바뀌어야 한다. 에이전트 제어 흐름을 급히 반쪽으로 바꾸면 조용한 버그가
  나기 쉬워, 설계를 갖춰 별도로 처리하는 편이 낫다고 판단했다.
- **언제부터 문제가 되나**: 원래 이 처리는 "조회 도구가 없어 실사용 빈도가 낮다"는 근거로
  미뤄져 있었는데, 2026-07-26 `listTodos` 추가로 **그 전제가 깨졌다.**
- **재현**: 오리에게 "남은 할 일 알려주고 우유 사기도 추가해줘"라고 한 문장으로 말한다.
- **현재 상태**: **고쳤다.** 조회를 먼저 실행해 답을 만들고, 변경은 담아 뒀다가 승인 카드와 함께
  올린다(agent.ts + useDuckChat). 변경이 승인 전에 실행되지 않는 성질은 테스트로 유지.
  실제 오리 응답은 로그인·쿼터가 필요해 실기 확인 미완 — 오리에게 "남은 할 일 알려주고
  우유 사기도 추가해줘"라고 한 문장으로 말해 조회 답과 승인 카드가 함께 나오는지 봐주면 된다.

## 24. (2026-07-26) 캘린더 위젯이 일정 500개를 넘으면 다가올 일정을 못 보여준다 [미해결·UI 결정 필요]

- **무엇을**: `listCalendarEvents`는 `start_at` **오름차순 500개**를 가져온다. 위젯은 그 전체를
  받아 화면에서 날짜별로 거른다. 그래서 **과거 일정이 500개를 채우면 다가올 일정이 목록에

- **오리 쪽은 고쳤다**(2026-07-26): 오리 전용 질의(`listEventsForDuck`)가 조건을 DB로 내려
  창 개념 자체를 없앴다. 위젯은 그대로다.
- **왜 지금 안 고쳤나**: 위젯의 범위를 좁히면(예: 최근 90일 이후만) **과거 날짜를 눌렀을 때
  일정이 사라진다.** 캘린더를 얼마나 과거까지 볼 수 있어야 하는지는 제품 결정이라,
  임의로 정하지 않았다.
- **선택지**: (a) 보고 있는 달 기준으로 범위를 잡아 다시 조회 — 정확하지만 달 이동마다 조회,
  (b) 최근 N개월 + 앞으로 전부 — 간단하지만 그보다 과거는 안 보임,
  (c) 지금 유지 — 500개 넘는 사용자에게만 문제.
- **재현**: 일정이 500개를 넘고 그중 대부분이 과거인 계정에서 캘린더 위젯을 연다.
- **현재 상태**: 오리는 정상, 위젯은 미해결.

## 40. (2026-07-26) 계정 삭제 — 켠 뒤에 확인 [사용자 확인 필요 · 되돌릴 수 없음]

**먼저**: 이 기능은 `SUPABASE_SERVICE_ROLE_KEY`를 넣기 전까지 **꺼져 있습니다**
([PENDING 9번](PENDING.md)). 안 넣으셨다면 확인할 것도 없습니다 — 그게 정상입니다.

**키를 넣기 전 확인(안전 확인)**
1. 설정 → 위험 구역에 **"계정까지 영구 삭제" 버튼이 안 보이는지** 봅니다.
2. 기존 "모든 데이터 삭제"는 그대로 있는지 봅니다(동작이 바뀌면 안 됩니다).

**키를 넣은 뒤 확인 — 반드시 버려도 되는 계정으로 하세요**
1. 버튼이 나타나는지 봅니다.
2. 눌러서 안내 문구가 **"로그인 계정과 이메일이 삭제된다"**고 분명히 말하는지 봅니다.
3. 확인 문구가 **"계정을 영구 삭제"**인지 봅니다(콘텐츠 삭제의 "삭제합니다"와 달라야 합니다).

**왜 사용자 확인이 필요한가**: 되돌릴 수 없는 동작이라 **제가 실행해 볼 수 없습니다.**
계약(순서·문구·키 미설정 시 차단·키 유출 금지)은 테스트로 잠갔지만, 실제 삭제가 끝까지
도는지는 진짜 계정으로만 확인됩니다.

**설계상 이런 점을 알아두세요**
- **콘텐츠를 먼저 지우고 계정을 마지막에** 지웁니다. 콘텐츠 삭제가 실패하면 **계정을 지우지
  않습니다** — 계정만 사라지고 데이터가 남는 게 최악이라서요.
- 그 반대 순서로 실패했을 때(데이터는 지워졌는데 계정 삭제 실패)는 **그 사실을 그대로
  알려 드립니다.** 숨기면 지금 상태를 모르게 됩니다.
- 30초 안에 다시 누르면 막습니다(되돌릴 수 없는 경로라 반복 호출 방지).

## 41. (2026-07-27) 비밀번호 재설정 — 메일이 실제로 오는지 [사용자 확인 필요]

**Task**: [Phase 41](../plans/phase_41.md) T3 — 비밀번호 재설정.

**먼저**: 이 흐름은 **Supabase 대시보드에서 Email provider를 켜야** 동작합니다
([PENDING 11번](PENDING.md)). 안 켜셨다면 재설정을 눌러도 "이메일 로그인이 아직 준비되지
않았습니다"만 뜹니다 — 그게 정상입니다.

**무엇을 확인하나**
1. `/login` 로그인 탭에서 이메일을 넣고 **"비밀번호를 잊으셨나요?"**를 누릅니다.
   → "재설정 메일을 보냈습니다…" 안내가 뜹니다.
2. **메일이 실제로 도착하는지** 봅니다(스팸함도 함께 — 무료 티어는 best-effort 발송입니다).
3. 메일의 링크를 누릅니다 → `/auth/reset`에서 **새 비밀번호 입력 폼**이 떠야 합니다.
4. 새 비밀번호를 넣고 바꾸면 **바로 로그인된 채 `/`로** 들어가집니다.
5. 로그아웃 후 **새 비밀번호로 로그인**되는지 봅니다.
6. **같은 링크를 한 번 더** 눌러 봅니다 → 폼 대신 "재설정 링크가 만료됐거나 이미
   사용됐습니다…" 안내가 나와야 합니다(1회용).

**왜 사용자 확인이 필요한가**: 메일 발송·수신은 코드가 확인할 수 없습니다. 제가 확인하면
실제 주소로 메일이 나가고(되돌릴 수 없는 외부 발송), provider가 꺼져 있어 어차피 안 나갑니다.
코드로 잠근 것은 여기까지입니다 — 오류 문구 판정(테스트 7건) · 세션 없이 폼이 렌더되지
않는 것(e2e) · 화면 렌더·레이아웃([스크린샷](screenshots/2026-07-27/password-reset/index.md)).

**알아두실 것**
- **가입 확인 메일과 재설정 메일이 같은 시간당 통을 씁니다**(프로젝트 전체 합산).
  연달아 여러 번 누르면 상한에 걸려 "시도가 너무 잦습니다"가 뜹니다 — 고장이 아닙니다.
- **결과를 "가입된 이메일입니다/아닙니다"로 구분해 말하지 않습니다(의도).** 그렇게 말하면
  어느 이메일이 가입돼 있는지 알려주는 통로가 됩니다. 없는 주소를 넣어도 같은 안내가 뜹니다.
- 재설정 화면은 **현재 비밀번호를 묻지 않습니다** — 잊어서 온 사람에게 물으면 성립하지 않습니다.
  대신 메일 링크로 받은 세션이 없으면 폼 자체가 열리지 않습니다.

## 42. (2026-07-27) 로그인 뒤 화면 3곳 — 눈으로 봐주세요 [사용자 확인 필요]

**Task**: [Phase 42](../plans/phase_42.md) T1·T4·T7 (2차 피드백 2-1·1-2·1-9).

**왜 제가 못 보나**: 셋 다 **로그인해야 보이는 화면**입니다. e2e 65건 중 46건이 세션이 없어
스킵되고, 그 안에 이 화면들이 있습니다(Phase 41 T5에서 시크릿 2개를 등록하시면 열립니다).
그래서 이번에는 **코드와 유닛 테스트까지만** 확인했습니다.

**봐주실 것**
1. **대시보드 인사말** — 설정에서 이름을 바꾼 뒤 대시보드를 열어 **"안녕하세요, 바꾼이름님"**이
   되는지. 전에는 왼쪽 사이드바만 바뀌고 인사말은 안 바뀌었습니다.

3. **사이드바 맨 아래** — 테마/걷기/로그아웃이 좁을 때 **줄바꿈되는지**.
   요청("로그아웃 버튼이 고정이라 유동적으로 아래로")을 **레이아웃 깨짐**으로 읽었습니다.

   추측으로 만들면 되돌리기 어려워서 만들지 않았습니다.

4. **대시보드 "오늘의 뉴스 TOP 3"** (2026-07-27 추가, T2) — 기사가 안 뜰 때 **뭐라고 하는지**

   - 수집 전이면 "아직 수집된 기사가 없어요"
   - 기사는 있는데 전부 오래됐으면 **"최근 기사가 없어요. 수집된 기사 N건은 발행일이 3일보다
     오래됐어요"** ← 사용자님이 겪으신 상황은 **이쪽**일 것입니다.
   전에는 어느 경우든 "최근 3일 안에 **수집된** 기사가 없어요"였는데, 방금 수집하셨으니
   그건 사실이 아니었습니다. 걸린 건 수집이 아니라 **발행일**이었습니다.

## 50. 대화 화면 구분선·스크롤 보호의 육안 확인 (2026-07-29, Phase 51 T6)

- **무엇을**: 대화 화면에 ① 날짜 구분선(오늘/어제/그 이전은 "2026년 7월 25일 (토)")
  ② "여기까지 읽었어요" 미읽음 구분선 ③ 위로 스크롤해 읽는 중 새 메시지가 오면
  화면을 끌어내리는 대신 "새 메시지 ↓" 버튼을 띄우는 동작을 넣었다.
- **왜 사용자 검증이 필요한가**: `/messages/[id]`는 로그인 뒤 화면인데 e2e 인증 세션
  파일(`apps/web/e2e/.auth/user.json`)이 없어 Playwright로 실물 스크린샷을 뜰 수 없다.
  날짜 경계·미읽음 판정은 core 순수 함수 테스트 24건으로 검증했지만 **실제 스크롤 감각**
  (버튼 위치·구분선 간격)은 눈으로만 확인된다.
- **재현 절차**: 메시지가 이틀 이상 쌓인 방을 연다 → 날짜 구분선이 날짜마다 하나씩 보이는지
  → 다른 계정(또는 오리)이 새 메시지를 보낼 때 위로 스크롤해 두면 화면이 튀지 않고
  하단 중앙에 "새 메시지 ↓" 버튼이 뜨는지 → 누르면 바닥으로 내려가는지.
  안 읽은 메시지가 있는 방을 열면 그 첫 메시지 위에 "여기까지 읽었어요" 선이 보이는지.
- **현재 상태**: 코드 완료·전체 테스트 green. 실물 확인 대기.

## 51. 전체화면 이미지 뷰어의 육안 확인 (2026-07-29, Phase 51 T5)

- **무엇을**: 대화의 사진을 누르면 전체화면 뷰어(이전/다음 화살표·키보드, "n / m" 위치,
  저장 버튼, Esc/배경 클릭 닫기)가 뜬다.
- **왜 사용자 검증이 필요한가**: 50번과 같은 이유 — e2e 인증 세션이 없어 로그인 뒤 화면을
  Playwright로 못 띄운다. 저장 버튼의 실제 파일 저장(브라우저 다운로드 동작)도 실기만 확인 가능.
- **재현 절차**: 사진 2장 이상 있는 방 → 사진 클릭 → 화살표(버튼·키보드)로 이동 →
  "저장" 누르면 webp 파일이 받아지는지 → Esc·배경 클릭으로 닫히는지 →
  (상대가) 보는 중 사진 삭제 시 뷰어가 스스로 닫히는지.
- **현재 상태**: 코드 완료·전체 테스트 green. 실물 확인 대기.

## 52. 방별 사진 모아보기의 육안 확인 (2026-07-29, Phase 51 T5)

- **무엇을**: 대화 헤더 "사진 모아보기" → 방 전체 사진 격자(최근 먼저) → 썸네일 클릭 시
  전체화면 뷰어. Esc로 (뷰어가 닫힌 상태에서) 모아보기 닫기.
- **왜**: 50·51번과 동일 — e2e 인증 세션 부재로 로그인 뒤 화면을 Playwright로 못 띄운다.
- **재현 절차**: 사진 여러 장 있는 방 → "사진 모아보기" → 격자에 다 나오는지(오래돼 대화
  창에서 안 보이는 사진 포함) → 썸네일 클릭 → 뷰어 이전/다음이 대화 순서와 같은지 →
  뷰어 닫으면 모아보기로 돌아오고 Esc가 먹는지.
- **현재 상태**: 코드 완료·전체 테스트 green. 실물 확인 대기.

## 53. 메시지 → 할 일·메모 변환의 육안 확인 (2026-07-29, Phase 52 T1)

- **무엇을**: 메시지 메뉴(...)에 "할 일로 만들기"·"메모로 저장". 실행하면 대화에
  '"..." 메시지를 할 일로 만들었어요' 회색 안내줄(system 메시지)이 남는다.
- **왜**: e2e 인증 세션 부재(50~52번과 동일). 만들어진 할 일이 투두 위젯에, 메모가 메모
  위젯에 실제로 보이는지는 대시보드를 눈으로 봐야 한다.
- **재현 절차**: 방에서 아무 메시지의 ... 메뉴 → "할 일로 만들기" → 회색 안내줄 확인 →
  대시보드 투두 위젯에 그 제목이 있는지. 200자 넘는 긴 메시지로도 한 번(제목이 …로
  줄고 뒤가 잘리는지). "메모로 저장"도 같은 방식.
- **현재 상태**: 코드 완료·전체 테스트 green. 실물 확인 대기.
