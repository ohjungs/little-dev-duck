## 1. OAuth 어댑터 기기 실기검증

- **Task**: Phase 10 — Google Calendar / GitHub 이슈 / Gmail 어댑터.
- **무엇을**: 로그인→provider_token 캡처→승인 카드→실제 외부 API 반영→감사 로그까지 end-to-end.
- **왜 사용자 필요**: 실제 OAuth 로그인 플로우·외부 계정 권한이 필요. 무인 세션은 브라우저 로그인 불가.
- **재현 절차**: 배포된 웹에서 Google/GitHub 로그인 → 설정에서 어댑터 연동 → 오리에게 "내일 회의 잡아줘"
  등 액션 요청 → 승인 카드 확인 → 실제 캘린더/이슈/메일에 반영됐는지 대조.
- **현재 상태**: Google Calendar는 2026-07-23 사용자 검증 통과(종결). GitHub 이슈·Gmail 어댑터는 코드 완료·미검증.

## 2. Sentry 계정 (Phase 13 T5 — PII 스크러빙)

- **무엇을**: Sentry 프로젝트 생성 + DSN 발급 → 에러 리포팅 + PII 스크러빙 구성.
- **왜 사용자 필요**: 외부 계정 생성·DSN은 사용자 몫. 무료 티어 원칙상 계정 소유자 결정 필요.
- **현재 상태**: 미착수(이월). DSN이 열리면 서버 env 주입 + 스크러빙 룰 구현 가능.

## 7. 정적 프리렌더 페이지의 CSP nonce 차단 — ✅ 해결됨 (2026-07-26, 사용자 "알아서 결정" 위임)

- **결정**: `/welcome`에 `export const dynamic = "force-dynamic"` 한 줄. 대안이던 "정적 공개 경로만
  CSP 완화"는 보안 미들웨어에 분기를 넣는 쪽이라 채택하지 않았다 — proxy.ts 주석대로 CSP는 과거에
  한 번 깨진 이력이 있는 민감 영역이고, 랜딩 트래픽 규모에서 per-request 렌더 비용은 무시할 수준이다.
- **검증**: CSP 콘솔 오류 **23건 → 0건**, 하이드레이션 `true`(desktop·mobile 양쪽), nonce 0개 → 1개.
  증거: `docs/loop-eng/screenshots/2026-07-26/phase18-csp-welcome/`.
- **부수 발견(같이 수정)**: CSP를 고쳐도 Analytics는 여전히 죽어 있었다. Vercel Analytics가 받아오는
  `/_vercel/insights/script.js`가 미들웨어 matcher에 걸려 **303으로 /welcome(HTML)을 돌려받고** 브라우저가
  "MIME type text/html is not executable"로 거부하고 있었다. matcher에 `_vercel` 제외를 추가해 해소
  (로컬은 플랫폼 파일이 없어 404가 정상, Vercel에서는 실제 스크립트가 서빙된다).
  → **랜딩 유입 지표를 막던 원인은 CSP와 matcher 2개였고 둘 다 수정됨.**

<details><summary>원래 보고 내용 (기록 보존)</summary>

- **무엇을**: `/welcome`(공개 랜딩)에서 **모든 스크립트가 CSP로 차단**된다. 실측:
  `curl /welcome | grep -c 'nonce='` → **0**, 그런데 응답 헤더는
  `script-src 'self' 'nonce-<uuid>' 'strict-dynamic'`. `strict-dynamic`이 있으면 `'self'`가 무시되므로
  nonce 없는 모든 `<script>`가 차단된다. 동적 라우트 `/p/[slug]`는 nonce가 2개 박혀 정상(대조 확인).
- **원인**: `/welcome`은 정적 프리렌더(`○ Static`)라 HTML이 빌드 시점에 고정된다. proxy.ts는 요청마다
  새 nonce를 발급하는데, 정적 HTML에는 그 nonce를 넣을 방법이 없다. (Next 공식 문서도 nonce는
  동적 렌더 페이지에서만 지원한다고 명시.)
- **영향**: 페이지 내용·스타일은 정상 렌더되지만(스크린샷 확인) 하이드레이션이 죽어 클라이언트
  상호작용·Next soft navigation·`<Analytics/>`(Vercel 웹 애널리틱스)가 동작하지 않는다.
  **획득(Acquisition) 지표를 랜딩에서 측정하지 못한다** — Phase 18의 목적과 정면으로 충돌.
- **왜 사용자 필요**: 고치려면 셋 중 하나를 골라야 하는데 전부 보안 태세(XSS 방어선) 변경이다.
  (a) `/welcome`을 강제 동적 렌더 → nonce 정상, 대신 랜딩 정적 캐시를 잃음(마케팅 페이지 성능/비용).
  (b) 공개 정적 경로에는 nonce·strict-dynamic을 빼고 `'self'`만 → 정적 페이지의 XSS 방어 약화.
  (c) 정적 페이지용 CSP를 빌드 타임 해시 기반으로 → 구현 복잡도 큼.
  proxy.ts 주석이 남기듯 CSP는 과거 실측으로 한 번 깨진 이력이 있는 민감 영역이라 자율 변경하지 않는다.
- **현재 상태**: **미수정, 기존 버그(이번 작업이 만든 것 아님)**. Phase 18 T1은 이 문제와 독립적으로
  완료(OG 카드·메타데이터는 스크립트 불필요). 재현: `next build && next start` 후 `/welcome` 콘솔.

## 8. 공개 페이지 실기 검증 — Supabase 자격증명 필요 (Phase 18 T1)

- **무엇을**: `/p/<slug>` 정상(ready) 상태와 진짜 404 상태의 화면, 그리고 카톡·슬랙·X에 링크를 붙였을 때
  OG 카드가 실제로 뜨는지.
- **왜 사용자 필요**: 로컬에 `.env.local`(NEXT_PUBLIC_SUPABASE_*)이 없어 공개 페이지 조회 자체가 안 된다.
  이번 스크린샷의 `public-page__notfound__*`는 의도한 404 UI가 아니라 **env 부재 에러 경계**다(코드 버그 아님).
  소셜 카드는 배포된 공개 URL을 크롤러가 읽어야 확인 가능(로컬 불가).
- **재현 절차**: ① 페이지를 "웹에 공개" → 링크 복사 ② 시크릿 창으로 열어 읽기 전용 확인
  ③ 그 링크를 카톡/슬랙에 붙여 오리 카드 + 한글 제목이 뜨는지 확인
  ④ https://cards-dev.twitter.com/validator 또는 슬랙 미리보기로 og:image 로딩 확인.
- **현재 상태**: 코드·빌드·메타데이터 검증 완료(og:image 200, 절대 URL 생성 확인). 실제 소셜 카드 육안 미검증.

## 9. OG 카드에 한글 제목 넣기 — 한글 폰트 자산 도입 결정 필요 (Phase 18 T1 축소분)

- **무엇을**: phase_18.md T1 수용 기준은 "OG 이미지에 페이지 제목"이었으나, 이번엔 **브랜드 카드**로만 구현.
- **왜 축소**: satori(next/og)는 글리프를 그리려면 폰트 버퍼가 필요한데 저장소에 한글 폰트가 없다
  (Geist=라틴 전용). 폰트 없이 한글 제목을 넣으면 전부 두부(□)로 깨진다.
- **왜 지금은 문제 아닌가**: 카톡·슬랙·X 모두 카드에서 **og:title을 텍스트로 따로 렌더**하므로 한글 제목은
  이미 사용자에게 보인다. 이미지 안 제목은 중복이다(ponytail).
- **결정 (2026-07-26, 사용자 "알아서 결정" 위임)**: **넣지 않는다. 브랜드 카드로 확정.**
  (a) Noto Sans KR 서브셋 TTF ~1.5MB 저장소 추가 — 이미 og:title로 보이는 텍스트를 이미지에 한 번 더
  그리자고 저장소에 1.5MB 바이너리와 라이선스 파일을 들이는 건 YAGNI.
  (b) 요청 시점 Google Fonts 글자 단위 서브셋 fetch — 외부 런타임 의존 + satori가 woff2를 못 읽어
  "구형 UA를 보내면 ttf를 준다"는 미문서화 동작에 기대야 한다. 카드가 조용히 깨질 경로를 만드는 셈.
  → 얻는 것(중복 텍스트)보다 잃는 것(용량·취약한 외부 의존)이 크다. 재검토 트리거: 사용자가 카드에
  제목이 없어 불편하다고 하거나, 저장소에 한글 폰트가 다른 이유로 이미 들어오는 경우.
- **현재 상태**: 브랜드 카드로 완료·검증됨(1200x630 PNG 정상 렌더 확인). **항목 종결.**
