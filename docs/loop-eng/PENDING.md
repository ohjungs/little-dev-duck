다만 **역할·기능 토글·카드 배치는 저장되지 않는다.**

적용 뒤 Supabase 어드바이저를 다시 돌리면 지적이 사라졌는지 확인된다.

```
cd apps/web
```

브라우저가 뜨면 실제로 로그인하고 창을 닫으면 됩니다(포트는 **반드시 5100**).

지금은 로그인 뒤 화면 테스트 **39건이 전부 건너뛰어집니다.** 세션 파일이 생기면 그때부터
자동으로 돌아갑니다 — 이 세션에서 만든 것 중 아래가 그 대상입니다.

- 반복 할 일(주기 표시·선택 폭·완료 시 이동) 6건
- 마감일(표시·입력 폭·하루 밀림 금지) 4건
- 삭제 되돌리기(같은 항목 복귀·스크린리더·연속 삭제) 4건
- 기존 위젯·반응형 테스트 25건

### 2026-07-26 갱신 — CI에서도 돌릴 수 있게 준비했습니다 (Phase 40)

위 방법(로컬에서 세션 파일 만들기)은 그대로입니다. **추가로 CI에서 돌리는 길이 열렸습니다.**

전에는 README가 "CI에 단계를 추가해야 한다"고만 적어 둬서, 시크릿을 등록해도 아무 일도
일어나지 않았습니다. 지금은 **받는 단계를 먼저 만들어 뒀습니다** — 세션 파일을 만드신 뒤:

```
base64 -w0 apps/web/e2e/.auth/user.json
```

이 값을 GitHub 저장소 Settings → Secrets and variables → Actions에
**`E2E_AUTH_STATE_B64`** 로 등록하면 그때부터 44건이 매 푸시마다 함께 돕니다.

- **등록 안 하셔도 지금과 똑같습니다**(미설정이 안전한 기본값) — 전부 스킵, 실패 아님.
- 내용은 **로그에 남기지 않습니다**(세션 토큰이라서). base64가 잘못되면 조용히 넘어가지 않고
  오류로 멈춥니다.
- **결정이 필요한 것**: 켜면 매 푸시마다 실제 Supabase에 투두·메모를 만들고 지웁니다
  (실패 시 잔여 데이터가 남을 수 있습니다). **전용 테스트 계정**을 따로 파시는 걸 권합니다 —
  본인 계정으로 돌리면 본인 데이터에 섞입니다.

**세션이 만료됐을 때도 이제 구분됩니다**: 전에는 만료된 파일이 있으면 스펙이 실행되어
리다이렉트로 실패해서 "세션 만료"와 "진짜 버그"가 같아 보였습니다. 지금은 만료를 감지해
**"갱신하세요"라는 사유와 함께 스킵**합니다.

## 6. 환경변수 하나 — keepalive를 완전히 잠그기

Vercel 프로젝트 설정 → Environment Variables → **`CRON_SECRET`** 추가(값은 아무 긴 임의 문자열).

`/api/keepalive`는 Supabase 무료 티어가 7일 무활동으로 일시정지되는 걸 막는 통로입니다.
코드는 `CRON_SECRET`이 **있으면** 그 값을 검사하도록 돼 있는데, 프로덕션에 값이 없어
지금은 **누구나 호출할 수 있습니다**(실측: 헤더 없이 200, 틀린 값으로도 200).

데이터가 새지는 않습니다 — RLS 때문에 0건이 돌아오고 아무것도 바뀌지 않습니다.
문제는 아무나 우리 서버를 통해 Supabase 호출을 반복시킬 수 있다는 점이고, 무료 등급에서는
Vercel 실행 횟수와 Supabase 요청량이 그대로 깎입니다.

2026-07-26에 코드 쪽에 시간당 호출 상한을 넣어 급한 불은 껐습니다. 다만 그 상한은 서버
인스턴스 메모리 기반이라 인스턴스가 여럿이면 느슨해집니다 — **완전한 차단은 이 환경변수**입니다.
값을 넣으면 코드가 자동으로 검사합니다(추가 배포 불필요, 다음 배포부터 적용).

Vercel Cron이 이 라우트를 부를 때 그 헤더를 자동으로 실어 보내므로 크론 쪽 수정은 없습니다.

  (붙어 있거나 `"use client"` 파일에서 읽으면 **테스트가 실패합니다.**)
- 라우트는 **요청 본문을 아예 읽지 않습니다.** 지울 대상은 세션에서 꺼낸 본인뿐입니다.
- 콘텐츠를 먼저 지우고 계정을 마지막에 지웁니다. 콘텐츠 삭제가 실패하면 **계정을 지우지
  않습니다** — 계정만 사라지고 데이터가 남는 상태가 최악입니다.
- 확인 문구가 콘텐츠 삭제("삭제합니다")와 **다릅니다**("계정을 영구 삭제") — 손이 기억한 대로
  눌러 계정까지 지우는 걸 막습니다.

**안 켜셔도 됩니다.** 다만 그동안은 가입한 사람이 자기 계정을 지울 방법이 없고,
MUST 항목이 미완으로 남습니다.

## 10. 판단만 해주시면 되는 것 — 남은 취약점 5건 (급하지 않음)

**2026-07-26: 취약점 14건 중 9건을 고쳤습니다.** Next.js를 `16.2.10 → 16.2.11`로 올렸습니다
(확정 스택 안의 패치 레벨이라 스택 변경이 아닙니다). 그 9건은 **공개 배포된 앱의 런타임에
실제로 걸리는 것들**이었습니다 — 프록시 우회, 서버 액션 DoS, SSRF 2건, 캐시 혼동, 내부 서버
함수 엔드포인트 노출 등.

**남은 5건은 전부 "고치는 쪽이 더 위험한" 부류라 측정하고 두었습니다.** 근거는 아래입니다.

| 패키지 | 건수 | 누가 끌어오나 | 왜 지금 노출이 아닌가 |
|---|---|---|---|
| `postcss` 8.4.31 / 8.5.19 | 3 | `next`가 8.4.31을 **정확히 고정**, `@tailwindcss/postcss`가 8.5.19 | 빌드 시점에만 돈다. 공격 경로는 **악의적 CSS를 빌드 입력에 넣는 것** — 우리 CSS는 저장소 안에 있고 빌드는 Vercel이 우리 저장소로만 돌린다 |
| `sharp` 0.34.5 | 1 | `next`의 optional 의존 | **남이 만든 이미지가 닿는 길이 없다**(코드로 확인): `next.config.ts`에 `remotePatterns`가 없어 Next가 원격 호스트를 전부 거부하고, `next/image`에 넘기는 값은 우리 `/duck-logo.png`뿐이다. 유일한 변수 src(`PageEditor`의 표지)는 `unoptimized`라 최적화 경로를 아예 안 거친다 |
| `brace-expansion` 1.1.16 | 1 | `minimatch@3` ← eslint 계열 | **개발·린트 때만** 쓴다. 배포 산출물에 들어가지 않는다 |

**왜 버전을 강제하지 않았나**: `pnpm.overrides`로 올리면 next·tailwind·eslint가 **시험해 본 적
없는 조합**이 됩니다. 특히 `brace-expansion`은 패치 버전이 `>=5.0.8`인데 이걸 요구하는
`minimatch@3`은 `^1.1.7`을 기대합니다 — **메이저 4단계 점프**라 린트가 통째로 깨질 쪽이 더
큽니다. `sharp`도 libvips를 품은 네이티브 패키지라 마이너 상향이 플랫폼별로 다르게 터집니다.

셋 중 하나를 정해 주시면 됩니다:

1. **그대로 둔다** (권장) — 위 근거대로 실제 노출 경로가 없습니다. 상위 패키지가 올라가면
   자연히 사라집니다.
2. **`postcss`만 올린다** — 셋 중 가장 안전합니다(같은 메이저 안). `pnpm.overrides`에
   `"postcss": "^8.5.20"` 한 줄이면 3건이 사라지고, 빌드·테스트로 검증됩니다.
3. **전부 강제한다** — 취약점 수는 0이 되지만 린트·이미지 처리가 깨질 수 있고, 그때는
   되돌려야 합니다.

`pnpm audit`은 **노출 경로를 보지 않고 버전만 봅니다** — 숫자를 0으로 만드는 것과 실제로
안전해지는 것은 다릅니다. 위 9건은 후자였고, 남은 5건은 전자입니다.

### 2026-07-26 갱신 — 이제 CI가 감시합니다 (Phase 39)

**이 항목은 여전히 "판단만 해주시면 되는 것"이지만, 그 사이 방치될 위험은 없어졌습니다.**
CI에 게이트를 걸었습니다 — `pnpm audit --prod --audit-level high --ignore-registry-errors`.

- **새 고위험이 런타임 의존에 들어오면 CI가 먼저 막습니다.** 이번처럼 한 세션 동안 아무도
  안 보는 상태가 다시 생기지 않습니다.
- 위 표의 5건 중 **런타임 트리에 있는 3건**(sharp 1 + postcss 2)만 사유와 함께 면제 목록에
  등재했습니다(`pnpm-workspace.yaml`). `brace-expansion`은 개발 의존이라 `--prod`가 자동으로
  제외하고, postcss의 moderate 1건은 기준선(high) 아래입니다.
- **면제에는 사유가 강제됩니다**(테스트가 잡습니다). 특히 sharp 면제는 "`remotePatterns`가
  없다"는 전제에 얹혀 있어서, **원격 이미지를 허용하면 테스트가 실패해 면제를 지우게 만듭니다.**

즉 위 세 선택지는 그대로 열려 있고, 아무것도 안 하셔도 **새 위험은 자동으로 걸립니다.**

## 11. 스위치 하나 — 이메일 로그인 켜기 (요청 0번)

**Supabase 대시보드 → Authentication → Providers → Email → 켜기.**

요청하신 이메일+비밀번호 로그인 화면을 만들어 배포했습니다([Phase 41](../plans/phase_41.md) T1).
`/login`에 Google·GitHub 아래로 이메일 폼이 붙었습니다(로그인·가입 탭).

**켜기 전까지 앱 동작은 안내 문구 하나 외에 바뀌지 않습니다.** 지금 폼을 제출하면
"이메일 로그인이 아직 준비되지 않았습니다. Google 또는 GitHub로 계속해 주세요."가 뜹니다 —
정체 모를 실패로 두지 않았습니다.

### 함께 정하실 것

1. **가입 시 메일 확인(Confirm email)을 켤지.** 켜면 아무 이메일로나 가입되는 것을 막지만
   무료 티어 발송 상한을 나눠 쓰게 됩니다.
   **2026-07-27 갱신 — 상한을 조사해 `CONSTRAINTS_FREE_TIER.md`에 넣었습니다.** 알아낸 것 중
   판단에 실제로 필요한 건 이겁니다: **가입 확인 메일과 비밀번호 재설정 메일이 같은 시간당
   통에서 나갑니다**(프로젝트 전체 합산). 즉 확인 메일을 켜면 **재설정 몫이 줄어듭니다.**
   정확한 시간당 건수는 문서가 동적 값으로 채워 원문에 숫자가 없었습니다 →
   **대시보드 Authentication → Rate Limits**에서 지금 값을 보실 수 있습니다.
   커스텀 SMTP를 붙이기 전에는 그 값을 바꿀 수 없습니다.

   로그인 탭의 **"비밀번호를 잊으셨나요?"** → 메일 링크 → `/auth/reset`에서 새 비밀번호.
