## 1. 아키텍처 관점 — 왜 3층인가

### 1-1. 층 분리의 근거는 샌드박스 제약이다

```
┌─────────────────────────────────────────────────────────┐
│ 러너            /loop 5m loop-eng                        │  타이머. 반복은 여기서만 일어난다
└───────────────────────┬─────────────────────────────────┘
                        │ 5분마다 깨움
┌───────────────────────▼─────────────────────────────────┐
│ 커맨드 층       loop-eng.md + loop-state.mjs             │  파일 I/O · 락 · 판단 안 함
└───────────────────────┬─────────────────────────────────┘
                        │ Workflow({args: 대장 3종})
┌───────────────────────▼─────────────────────────────────┐
│ 사이클 워크플로  loop-eng-cycle.js                        │  라운드·게이트 · 파일 안 만짐
└───────────────────────┬─────────────────────────────────┘
                        │ workflow() / agent()
┌───────────────────────▼─────────────────────────────────┐
│ 에이전트         구현·리뷰·렌즈·화면                       │  판단·구현
└─────────────────────────────────────────────────────────┘
```

이 분리는 미학이 아니라 **강제된 것**이다. 근거 두 개:

1. **워크플로 샌드박스에 파일 I/O가 없다.** 따라서 대장을 읽고 쓰는 주체는 커맨드 층일 수밖에 없다.
2. **워크플로 실행이 끝나면 메모리가 통째로 사라진다.** 따라서 무한 루프를 스크립트 안에 넣을 수 없다.
   `loop-eng-cycle.js`는 이름 그대로 **한 사이클**이고, 반복은 바깥 타이머가 담당한다.

결과적으로 **사이클 사이에 남는 것은 파일뿐**이다. 이게 다음 절의 대장 계약으로 이어진다.

### 1-2. 상태는 전부 append-only 원장(ledger)이다

루프는 산문 문서를 읽지 않는다. 읽는 것은 JSONL 세 개다.

| 파일 | 쓰는 주체 | 성격 | 무엇 |
|---|---|---|---|
| `docs/plan-ledger.jsonl` | `/plan` · `apply-cycle` | 판단 원장 | 할 일 후보 · 확정/기각/완료 |
| `docs/loop-eng/cycles.jsonl` | `apply-cycle` | 이력 원장 | 사이클마다 한 줄 — 무엇을 골랐고 어떤 게이트를 통과했나 |
| `docs/loop-eng/manual-open.jsonl` | `defer` | 보류 원장 | 사람 손이 필요해 자동 착수를 막은 것 |

**append-only + 뒤 줄이 이긴다(field-merge)**가 규칙이다. 같은 `titleKey`가 여러 줄로 쌓이고,
읽을 때 병합한다. 이벤트 소싱에 가까운 모델이고, 장점은 이력이 안 사라지는 것, 대가는
읽을 때마다 병합·중복 제거 비용이 든다는 것이다.

`Status.md`·`History.md`는 **사람이 읽는 산문**이라 루프가 읽지 않는다(Status.md 실측 1,043줄 —
매 사이클 통째로 넘기면 토큰을 직접 태운다). 대신 코드가 좁은 통로 둘로만 잇는다:

- **유입** — Status.md 백로그의 미완 항목 중 대장에 없는 것을 뽑아 `confirmed`로 올린다
- **배출** — 사이클 사실 요약을 `<!-- LOOP-STATUS:BEGIN/END -->` 구간에 갈아끼운다

### 1-3. 관통하는 설계 원칙 셋

**HD-003 — 결정적 작업은 코드로.** 이 하네스 전체를 관통하는 축이다. 렌즈 실행 여부 판정,
연속 실패 계산, 시크릿 가리기, Status.md 백로그 파싱이 전부 코드다. LLM은 판단·구현·리뷰에만 쓴다.

**HD-010 — 산출물 우선.** 보고 전에 파일로 남긴다. 스크린샷도, 사이클 기록도.
리포트 스트림이 잘려도 산출물이 남게.

**"산문 지시는 조용히 빠뜨려진다".** 문서 곳곳에 실측 사고 기록이 달려 있고, 그때마다 대응은
같다 — 산문을 코드로 접었다. 실제 사례:

| 산문이던 것 | 관측된 결과 | 코드로 접은 방식 |
|---|---|---|
| 보류에 `itemKey`를 적어라 | 110건 중 1건만 지켜짐 | `defer`가 없으면 거부(fail-closed) |
| 해소되면 목록에서 지워라 | 113건 중 4건만 표시 | `resolve` 서브커맨드 |
| 22렌즈 다 돌려라 | 3개만 돌고 "통과" 주장 가능 | 렌즈를 키로 만들고 스키마로 실행 여부 수집 |
| Status.md를 갱신하라 | 14사이클 내내 반영 0건 | `apply-cycle`이 마커 구간을 기계 갱신 |
| 락 살아있음 표시를 밀어라 | 한 번도 갱신 안 됨 | `lock refresh` 서브커맨드 |

## 2. 구조 관점 — 한 사이클이 어떻게 도는가

### 2-1. 여섯 단계

```
DECIDE ─→ ORIENT ─→ BUILD ─→ TEST20 ─→ VISUAL ─→ ACT
  │         │         │        │         │        │
 대장     유효성    하위     22렌즈    Playwright  게이트
 후보     재확인   하네스    5그룹      스크린샷   판정
 선정             (라운드)   병렬       (UI일 때)
```

**DECIDE** — 코드만 돈다. LLM 없음. 대장에서 후보를 거르는 필터 다섯 개:

```
confirmed인 것
  → done/rejected 제외
  → 이미 통과한 사이클이 있는 것 제외
  → 연속 실패 3 이상 제외          (사이클을 넘어 적용)
  → 보류 목록에 있는 것 제외        (itemKey + 제목 양방향 대조)
  → 되돌리기 어려운 것은 approved:true 없으면 제외
  → severity 정렬 (S1 → S2 → S3)
```

이 정렬은 나중에 붙었다. 그전에는 후보 순서가 **대장 파일 순서(= 발굴 순서)**여서 S1 보안 항목이
뒤로 밀렸다.

**ORIENT** — 고른 항목이 아직 유효한지 재확인한다(stale 가드). 이미 구현됐으면 대장에 `done`으로
올리고 다음 후보로. 최대 3회 시도.

**BUILD** — `dev-harness-loop` 워크플로에 위임. 아래 2-3.

**TEST20** — 22개 렌즈를 5그룹으로 묶어 병렬. 아래 2-2.

**VISUAL** — `check.hasUI`일 때만. Playwright로 화면을 띄우고 스크린샷을 **먼저 파일로 저장한 뒤** 보고.

**ACT** — 게이트 판정 후 사이클 기록 **객체**를 만들어 돌려준다. 파일에 쓰는 건 커맨드 층.

### 2-2. TEST20 — 렌즈 22개, 그룹 5개

22개를 22콜로 나누면 예산이 터진다. 같은 판단자가 볼 수 있는 것끼리 묶어 5콜로 만든다.

| 그룹 | 에이전트 | 렌즈 | UI 전용 |
|---|---|---|:---:|
| `gates` | test-automator | regression | |
| `input` | debugger | normal-path · boundary · null-empty · type-coercion · negative-overflow · unicode | |
| `state` | debugger | concurrency · idempotency · error-path · state-transition · async-order · network-failure · large-pagination | |
| `security` | security-auditor | authz · injection · secret-leak · backward-compat · data-integrity | |
| `ui` | ui-ux-designer | a11y · responsive · ui-states | ○ |

**판정 3단 분리가 이 장치의 핵심이다.**

```
missing   — 아예 보고 안 된 렌즈       → 하네스 결함 신호
notRun    — 봤다고 하지 않은 렌즈      → 정직 신호
notApplicable — 이번 변경이 그 축을 안 건드림 → 미실행도 실패도 아님
failed    → hardFailed(통과 차단) / softFailed(통과시키되 followUps로 적재)
```

```js
test20Complete = missing.length === 0 && notRun.length === 0
test20Green    = test20Complete && hardFailed.length === 0
```

**하드 렌즈 6개** — `regression` `authz` `injection` `secret-leak` `backward-compat` `data-integrity`.
나머지 16개는 소프트. 소프트 실패는 버리지 않고 `followUps`로 돌려 대장에 새 `confirmed` 항목이 된다.
흘리면 "완화된 게이트"가 그냥 검사를 안 하는 것과 같아지기 때문이다.

이 하드/소프트 분리도 나중에 붙었다. 그전에는 22렌즈 전부 통과를 요구했고, **5사이클 연속 통과
0건**이 나왔다 — 산출물은 매번 typecheck·lint·테스트 green이었는데도. 게이트가 "이 작업이 끝났나"가
아니라 "코드베이스가 22축에서 완벽한가"를 묻고 있었던 것이다.

### 2-3. BUILD — 하위 하네스의 라운드 루프

```
while (stopReason === null):
  round > hardCap                     → HARD_CAP
  Design(도메인별 병렬) → Develop(병렬) → Test → Review(code·sec·ux 병렬)
  green && 전원 APPROVE  → 다음 항목 (전부 끝나면 SUCCESS)
  아니면                → Debug → 라운드 재시작
  연속 디버그 실패 3회    → 재계획(Escalate)
  재계획 2회 초과        → HOLD
```

| 상수 | 값 | 의미 |
|---|---:|---|
| `CAP_ARG` | 호출자 지정(기본 8) | 라운드 상한의 출발점 |
| 실효 상한 | `min(12, max(CAP_ARG, 항목수 + 2))` | 항목 수보다 작으면 SUCCESS가 산술적으로 불가능 |
| `ROUND_CEILING` | 12 | 절대 상한 |
| `DEBUG_LIMIT` | 3 | 연속 디버그 실패 → 재계획 |
| `REPLAN_LIMIT` | 2 | 재계획 초과 → HOLD |

`stopReason`은 그대로 사이클의 `gates.review`가 된다. `SUCCESS`가 아니면 `build:false`다.

### 2-4. 발굴(discover) 모드

후보가 하나도 없으면 사이클은 구현 대신 발굴을 돈다. `dev-harness-plan` 워크플로 하나에 위임하고,
**한 사이클은 구현이든 발굴이든 하나만** 한다(둘 다 부르면 예산이 터진다).

```
Explore(감사관 병렬 스윕) → Design(제안 종합) → Review(교차검증) → Plan(우선순위) → Deliver(스펙 초안)
                    └── 신규 발굴 없는 라운드 2회 연속이면 정지(DRY_LIMIT)
```

교차검증은 세 갈래로 병렬이다 — 증거 검증(debugger) · 외부 조사(technical-researcher) ·
가치 반박(task-decomposition-expert). 과거 확정·기각분을 `ledger`로 넘겨 같은 것을 다시 발굴하지 않게 한다.

### 3-2. 모델 티어 배분

에이전트 정의 파일 대부분이 `model` 미지정이라 **세션 모델을 그대로 물려받는다**.
Opus 세션에서 루프를 켜면 사이클당 수십 개가 전부 Opus로 돈다. 그래서 **호출부에서 지정**한다
(정의 파일을 고치면 다른 프로젝트까지 바뀌므로).

| 티어 | 어디에 |
|---|---|
| `opus` | dev-harness-loop의 설계 종합(context-manager) |
| `sonnet` | 유효성 확인 · 렌즈 5그룹 · 화면검증 · 구현 · 리뷰 — 대부분 |
| `haiku` | 값싼 분류 |

### 3-3. 동시성 안전 3중 장치

| 장치 | 파일 | 막는 것 |
|---|---|---|
| 프로젝트 락 | `.claude/loop-eng.lock` | 같은 repo에 루프 둘 |
| 머신 레지스트리 | `~/.claude/loop-eng/active.json` | 머신 전체 동시 3개 이상 (상한 2) |
| 워크트리 분리 | git worktree | 같은 repo 진짜 병렬 |

락 임계값은 **90분**이다. 10분 → 30분 → 90분으로 두 번 올렸다. 이유가 구조적이다 —
**워크플로가 도는 동안에는 살아있음 표시를 밀어줄 주체가 없다.** 샌드박스에 파일 I/O가 없고
커맨드는 결과를 기다린다. 그래서 한 사이클 도는 동안 표시가 멈춰 있는 것이 정상이고,
90분이 그 공백을 감당한다.

`pid=`는 생존 판정에 **쓸 수 없다**. 거기 적히는 건 `loop-state.mjs`(한 번 쓰고 끝나는 헬퍼)의
pid라 읽는 시점엔 항상 죽어 있다.

### 3-4. 보안·개인정보 장치

| 장치 | 무엇 | 계기 |
|---|---|---|

### 4-3. 구조적 결함 3가지 (미해결)

**① 보고 결함이 항목을 매장한다.**
`missing`/`notRun`이 하드 실패와 **같은 무게**로 게이트를 막는다. 정직성 장치로는 옳지만,
잡히는 건 하네스의 보고 결함인데 벌은 항목이 받는다. `failed`가 쌓여 3회면 그 항목은
후보에서 빠져 사람 판단 대기로 넘어간다.

현재 연속 실패 2인 항목 3개. 그중 AdminUserPanel은 두 번 다 `blocked`이고 **항목 잘못이 하나도 없다**
(세션 종료 · 타 세션 커밋).

**② 락이 다른 하네스를 못 막는다.**
락은 `/loop-eng` 인스턴스끼리만 막는다. `/spec-loop`나 손으로 돌리는 세션은 그대로 들어온다.
사이클 7과 15가 이것으로 오염됐다. 15에서는 다른 세션의 `git add -A`가 이 사이클의 산출물까지
함께 커밋했다.

**③ 세션 사용량 한도.**
사이클당 537만 토큰·4.1시간이면 한도에 닿는다. 사이클 9는 통째로, 사이클 15는 렌즈 그룹 3개와
화면검증이 죽었다. 코드로 못 고치고, 사이클을 가볍게 하거나 시간대를 골라야 한다.

## 5. 종합 평가

### 강점

- **층 분리가 제약에서 유도됐다.** 취향이 아니라 샌드박스 한계에서 나온 구조라 흔들릴 이유가 적다
- **상태가 파일이고 append-only다.** 세션이 죽어도 이력이 남고, 다음 사이클이 백지에서 시작하지 않는다
- **결정적 판정을 LLM에서 걷어냈다.** 렌즈 누락·연속 실패·시크릿 가리기가 전부 코드다
- **실패에서 배운 흔적이 코드 주석에 남아 있다.** 거의 모든 상수에 "왜 이 값인지"와 실측 근거가 붙어 있다
- **자기 검사기를 갖고 있다.** 문서-코드 드리프트를 기계가 잡는다

### 약점

- **게이트가 하네스 결함과 코드 결함을 구분하지 않는다.** 통과율 7%의 상당 부분이 이것
- **비용이 크다.** 사이클당 537만 토큰은 세션 한도와 정면충돌한다
- **동시성 방어가 자기 종류만 막는다.** 다른 하네스·사람 세션은 통과한다
- **산문과 코드가 계속 벌어진다.** 검사기가 잡는 건 상수뿐이고, "누가 무엇을 부르는가" 같은 서술은
  못 잡는다(marketing-skills 사례가 그렇게 2주를 살아남았다)

### 성숙도

| 축 | 평가 |
|---|---|
| 상태 관리 | 성숙 — 원장 3종 + 스크리닝 + 회전 |
| 게이트 정의 | 성숙 — 하드/소프트 분리, 미보고 강제 |
| 게이트 **귀책 판정** | 미성숙 — 외부 원인과 코드 결함이 섞인다 |
| 동시성 | 부분적 — 자기 종류만 |
| 비용 관리 | 미성숙 — 상한은 있으나 실측이 상한을 넘는다 |
| 관측성 | 개선됨 — 2026-08-03에 Status.md 자동 배출 추가 |
