# SEC — SSRF 사설대역 가드가 IPv6 표기로 우회된다 (2026-07-30 `/loop-eng`)

> 산출물 우선(HD-010). 조사·실측 → 수정 순서로 기록한다.

## 요약

`packages/api/src/news.ts`의 `PRIVATE_HOST` 정규식은 **점 표기 IPv4만** 제대로 막는다.
IPv6 표기로 감싸면 **클라우드 메타데이터(169.254.169.254)를 포함해 전부 통과**한다.

이 가드는 사용자가 등록한 피드 URL로 **서버가 직접 fetch**하는 경로에 있다
(`addFeed` 등록 시 + `collectFeed`의 리다이렉트 최종 도착지). 즉 통과하면 서버가 내부망으로
요청을 보낸다.

## 착수 배경

Status backlog: `security: SSRF 사설대역 차단 IPv4 대체표기 커버리지 테스트로 고정`.
그 전제를 먼저 실측했더니 **IPv4 대체표기는 이미 안전**했고, 대신 다른 구멍이 나왔다.

## 실측 1 — IPv4 대체표기는 이미 막힌다 (백로그 전제 정정)

가드가 `new URL(url).hostname`을 쓰기 때문에 **WHATWG URL 파서가 IPv4를 점 표기로 정규화한
뒤** 정규식에 도달한다. 그래서 다음은 전부 차단된다:

| 입력 | 파싱된 hostname | 결과 |
|---|---|---|
| `http://2130706433/` (10진수) | `127.0.0.1` | 차단 |
| `http://0x7f000001/` (16진수) | `127.0.0.1` | 차단 |
| `http://0177.0.0.1/` (8진수) | `127.0.0.1` | 차단 |
| `http://127.1/` (짧은 표기) | `127.0.0.1` | 차단 |
| `http://0/` | `0.0.0.0` | 차단 |
| `http://2852039166/` (메타데이터 10진수) | `169.254.169.254` | 차단 |

**즉 백로그가 요청한 것은 "구멍 막기"가 아니라 "이 사실을 테스트로 고정"이다.** 고정할 값이
있다 — 누군가 호스트 추출을 `new URL().hostname`에서 원문 문자열로 바꾸면 위 6건이 **한꺼번에
조용히 열린다.** 지금은 그걸 막아 주는 검사가 없다.

## 실측 2 — IPv6 표기는 우회된다 (신규 발견, SEC)

| 입력 | 파싱된 hostname | 결과 |
|---|---|---|
| `http://[::ffff:169.254.169.254]/latest/meta-data/` | `[::ffff:a9fe:a9fe]` | **통과** |
| `http://[::ffff:127.0.0.1]/` | `[::ffff:7f00:1]` | **통과** |
| `http://[::ffff:10.0.0.1]/` | `[::ffff:a00:1]` | **통과** |
| `http://[::ffff:192.168.0.1]/` | `[::ffff:c0a8:1]` | **통과** |
| `http://[::]/` | `[::]` | **통과** |
| `http://[fe80::1]/` | `[fe80::1]` | **통과** |
| `http://[64:ff9b::127.0.0.1]/` | `[64:ff9b::7f00:1]` | **통과** |

대조군(정상 동작 확인): `[::1]`·`[0:0:0:0:0:0:0:1]`·`[fc00::1]`·`[fd00::1]`은 차단된다.

### 왜 새는가 — 정규식의 `::ffff:` 분기는 죽은 코드다

정규식은 `::ffff:(127\.|10\.|192\.168\.|169\.254\.|172\.…)`로 **점 표기를 기대**한다.
그런데 WHATWG URL 파서는 `::ffff:127.0.0.1`을 **16진수로 압축**해 `::ffff:7f00:1`로 만든다.
따라서 이 분기는 `hostname`에 대해 **절대 매칭될 수 없다.** 작성 당시엔 원문 문자열을
가정했던 것으로 보이는데, 실제로는 정규화된 값이 들어온다.

`::`(미지정)와 `fe80::/10`(링크 로컬)은 애초에 목록에 없다. `::`는 연결 시 루프백으로 간다.

### 심각도 판단 (과장하지 않음)

- **가장 위험한 것은 메타데이터 우회다.** 주석이 `169.254.169.254`를 이름까지 적어 막겠다고
  선언했는데 IPv6로 감싸면 뚫린다 — 선언과 실제가 갈라진 경우다.
- 다만 **Vercel 서버리스에는 EC2/GCE식 인스턴스 메타데이터 서비스가 없다.** 그래서 즉시
  자격증명이 새는 상황은 아니다. 위험은 (a) 내부 서비스 스캔·접근 (b) 다른 런타임으로 옮기거나
  자체 호스팅할 때 그대로 뚫린 상태로 따라간다는 점이다.
- 악용에 로그인이 필요하다(피드 등록은 인증 경로). 프로필이 3개(admin·admin·user)인 지금
  "사용자 1명이라 노출 없음" 논리는 쓰지 않는다.

## 수정 방향

정규식에 IPv6 문자열을 더 얹는 방식은 같은 함정을 반복한다(압축 표기 조합이 많다).
**hostname을 정규화해 숫자로 판정한다** — IPv6를 8그룹으로 펼친 뒤:

- 전부 0 → `::` 차단
- 마지막만 1이고 나머지 0 → `::1` 차단
- 앞 5그룹 0 + 6그룹 `ffff` → IPv4 매핑. 뒤 32비트를 점 표기 IPv4로 되돌려 **IPv4 규칙 재사용**
- `64:ff9b::` (NAT64 well-known) → 같은 방식으로 뒤 32비트를 IPv4로 판정
- 1그룹이 `fe80` → 링크 로컬 차단
- 1그룹 상위 7비트가 `fc00::/7` → 유니크 로컬 차단

IPv4는 기존 규칙을 그대로 쓴다(이미 정상 동작하며 실측으로 확인됨).

## 수정 결과

`PRIVATE_HOST` 정규식 → `isPrivateHost(hostname)` 함수로 교체. 호출부 4곳 전부 전환
(피드 등록 · 자동 발견 후보 · 자동 발견 리다이렉트 · 수집 리다이렉트 최종 도착지).

IPv4 규칙(`PRIVATE_IPV4`)은 옛 것을 **그대로** 유지했다 — 실측으로 정상 동작을 확인했고,
바꿀 이유가 없는 것을 바꾸면 검증 부담만 늘어난다.

### 남긴 한계 (정직하게)

- **DNS 리바인딩은 여전히 막지 않는다.** 호스트명이 공인 IP로 해석되는 척하고 실제 연결 시
  사설 IP로 바뀌는 공격이다. 막으려면 해석된 IP를 붙잡아 소켓 단계에서 검사해야 하는데
  (`lookup` 훅 + 커스텀 agent) Vercel 런타임에서 검증이 필요하다. 옛 주석의 YAGNI 판단을
  그대로 유지한다 — 이번 수정은 **문자열 표기 우회**를 닫은 것이고 그 범위를 넓히지 않았다.
- 이 가드는 hostname이 **이미 `new URL()`로 정규화됐다는 전제**에 얹혀 있다. 그 전제를
  테스트가 드러내 두었지만(대체표기 6건), 전제 자체를 강제하는 장치는 없다.
