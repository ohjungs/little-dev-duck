## post-redirect-get 기본 상태코드

- `NextResponse.redirect()`를 상태코드 없이 쓰면 기본값 307이 원 요청 메서드(POST)를 유지해,
  GET만 받는 라우트로 리다이렉트 시 405가 난다. 상태 변경(POST/PUT/DELETE) 핸들러의 리다이렉트는
  항상 303을 명시해야 한다.
- 최초 발견: 2026-07-20 / 마지막 재발견: 2026-07-20 / 재발견 횟수: 1회 (같은 세션 내 2곳: logout, proxy)
- 상태: active

## nonce 기반 CSP는 정적 프리렌더링 페이지에서 무효

- 미들웨어가 요청마다 nonce를 발급해 `script-src 'nonce-...'`에 싣는데, 그 페이지가 정적 프리렌더링
  (`○`)되면 빌드 시점에 한 번 구워진 스크립트 태그의 nonce가 매 요청 헤더 nonce와 영영 불일치해
  프로덕션에서 모든 스크립트가 CSP에 막힌다(로그인 완전 불능). 실제로 발생: `/login`이 정적이라
  위젯/브라우저에서 로그인이 깨졌고, 콘솔에만 CSP 위반이 대량으로 떴다.
- 교훈: (1) nonce 기반 CSP를 쓰는 페이지는 반드시 동적 렌더링이어야 한다(`export const dynamic =
  "force-dynamic"`). (2) CSP 도입 시 `curl`의 응답 헤더 값만으로는 이 버그를 못 잡는다 — nonce가
  매번 달라지는 것 자체는 정상으로 보이므로, 정적/동적 라우트별로 실제 브라우저(또는 body의 script
  nonce와 헤더 nonce 일치까지)로 검증해야 한다. 실사용자가 위젯에서 발견해줬다.
- **2026-07-26 재발견(2회째)**: `/_not-found`가 정적(`○`)이었다. 로그인한 사용자가 삭제된
  링크·오타로 없는 주소를 열면 그 화면의 스크립트가 전부 막힌다(문구는 보이고 하이드레이션이 죽음).
  `/login`처럼 치명적이진 않지만 **같은 함정을 두 번째로 밟았다.**
  - **왜 또 밟았나**: 1회차 교훈이 "force-dynamic을 붙여라"였는데 **붙었는지 확인하는 장치가
    없었다.** 새 페이지를 추가하면 기본값이 정적이라 아무도 모르는 사이 다시 생긴다.
  - **이번엔 검사로 만들었다**: `apps/web/e2e/buildStaticGuard.ts`가 빌드 산출물
    (`prerender-manifest.json`)에서 정적으로 구워진 HTML 페이지를 찾아 e2e 시작 전에 막는다.
    그 검사가 곧바로 `/_global-error`도 잡았는데, **Next 내장이라 고칠 수 없어**
    (커스텀 `global-error.tsx`는 `"use client"`라 `dynamic`을 못 받는다) 사유와 함께 허용 목록에 뒀다.
  - **검증의 한계(정직하게)**: 빌드 출력이 `○`→`ƒ`로 바뀌는 것과 가드 동작은 확인했지만,
    **브라우저 콘솔에 CSP 위반이 없는지는 못 봤다** — 404는 로그인해야만 보인다(비로그인은
    미들웨어가 `/welcome`으로 303). 스펙은 써 뒀고 세션 파일을 기다린다.
- 최초 발견: 2026-07-21 / 마지막 재발견: 2026-07-26 / 재발견 횟수: **2회**
- 상태: active (가드: `apps/web/e2e/buildStaticGuard.ts` — 2026-07-26 신설)
- 커밋: 4de6028(nonce 전환), accc4e3(force-dynamic 분리), d1414ce(not-found + 가드)

## 미적용 마이그레이션의 컬럼을 insert payload에 무조건 실으면 그 테이블 쓰기가 통째로 죽는다

- 2026-07-26 Phase 20에서 `todos.recurrence` 컬럼을 추가하는 마이그레이션과 함께 `createTodo`가
  `recurrence: input.recurrence ?? null`을 **항상** payload에 담도록 바꿔 배포했다. 그런데
  마이그레이션은 DDL이라 사용자 확인 대기 상태였고 실서버 `todos`에는 그 컬럼이 없었다.
  PostgREST는 insert payload에 존재하지 않는 컬럼이 있으면 **요청 전체를 거부**하므로,
  반복을 쓰지 않는 **평범한 할 일 추가까지 실패**하는 상태로 배포됐다.
- 왜 안 잡혔나: 하위호환은 **읽기 경로만** 챙겼다(`fromRow`에서 `row.recurrence ?? null`,
  zod `.default(null)`). 테스트도 가짜 클라이언트라 실제 스키마를 모르고, 오히려
  "반복이 없으면 null로 저장한다"는 **잘못된 동작을 고정하는 단언**이 들어 있었다.
- 교훈:
  1. **마이그레이션이 적용되기 전에 배포되는 코드는 새 컬럼을 쓰지 않아야 한다.**
     값이 있을 때만 키를 넣는다 — `...(x ? { col: x } : {})`. 그러면 미사용 시 payload가
     마이그레이션 이전과 완전히 동일해진다. null을 넣는 것과 키를 빼는 것은 전혀 다르다.
  2. 하위호환 검토는 읽기·쓰기 **양방향**으로 한다. 읽기만 보면 절반이다.
  3. 계약을 바꿀 때 **실제 배포 DB의 스키마를 확인**한다. 마이그레이션 파일이 있다는 것과
     적용됐다는 것은 다르다(`information_schema.columns` 조회로 확인 가능).
- 최초 발견: 2026-07-26 / 재발견 횟수: 0회
- 상태: active
- 커밋: (같은 세션에서 수정 — createTodo·restoreTodo 조건부 삽입 + 회귀 테스트 6건)

## Date를 거쳐 날짜 문자열을 만들면 시간대만큼 하루가 밀린다 (양방향 함정)

같은 뿌리에서 두 방향으로 터진다. 2026-07-26에 캘린더·통계·스탠드업에서 연달아 발견했다.

**(A) 만들 때** — `localDate.toISOString().slice(0, 10)`은 **UTC 날짜**다.
- 통계의 주간 경계: 로컬 자정 월요일을 `toISOString()`으로 잘라 **일요일**이 나왔다.
  KST에서 "이번 주" 창이 통째로 하루 밀린 채 집계되고 있었다.
- 스트릭: 오늘을 UTC로 잘라 얻는데 비교 대상 `checkedDate`는 로컬 날짜라, KST 00:00~09:00에
  "오늘" 키가 어제 것이 됐다.
- 서버(Vercel=UTC)의 스탠드업 날짜: 같은 이유로 KST 새벽엔 어제 날짜로 적혔다.

**(B) 읽을 때** — `new Date("2026-07-28")`처럼 **날짜만 있는 ISO는 UTC로 해석**된다.
- 캘린더가 이 방식으로 저장해, 한국에서 되읽으면 09:00이 됐다. 화면은 자정이면 시각을
  숨기도록 짜여 있었는데도 **날짜만 고른 일정마다 "오전 9:00"이 붙었다.**

**교훈**
1. 날짜 문자열이 필요하면 **Date를 거치지 않거나**(문자열·epoch day로 계산),
   **로컬 포맷터를 쓴다**(`toLocalDateString`·`todayIso`·`kstDateString`).
   `toISOString().slice(0,10)`은 "UTC 날짜가 맞을 때"만 쓴다.
2. 날짜만 있는 문자열을 파싱할 땐 `T00:00:00`을 붙이거나 숫자 인자 생성자를 쓴다.
3. **저장 규약은 읽는 방식에 맞춰야 한다.** 할 일 마감일은 화면이 문자열을 잘라 비교하니
   UTC 자정이 맞고, 캘린더는 `getHours()`로 읽으니 로컬 자정이 맞다. 규약이 다른 건 정상이고,
   **다르다는 사실을 주석으로 남기지 않는 게 문제**다.
4. **KST에서는 멀쩡해 보이고 음수 오프셋 지역에서만 깨지는 변형**이 있다(`getDay()` 계열).
   테스트는 실행 시간대에 의존하지 않게 짠다 — 기준 날짜를 문자열로 주입하고, 저장 문자열이
   아니라 되읽은 로컬 시/분으로 단언한다.
5. 이 저장소는 이미 세 곳에서 제대로 하고 있었다(`HabitWidget` 수동 포맷, `HabitHeatmap`의
   `+ "T00:00:00"`, Phase 19의 `kstDateString`). **한 곳을 고칠 때 같은 부류를 전수로 훑어야**
   나머지가 남지 않는다 — 이번에도 첫 발견 뒤 스윕에서 3건이 더 나왔다.

- 최초 발견: 2026-07-26 / 재발견 횟수: 3회 (캘린더 → 통계 3건 → 스탠드업 2건 → **내가 낸 회귀 2건**)
- 상태: active

**추가(2026-07-26, 같은 날 재발)** — 저장 규약을 고치면 **읽는 쪽을 전수로 훑어야 한다.**
캘린더 저장을 UTC 자정 → 로컬 자정으로 바꾸면서(위 (B) 수정), 같은 컴포넌트에서 날짜를
**UTC로 읽던 두 곳**(D-day 배지의 `daysUntil(startAt, ...)`, 표시용 `startAt.slice(0,10)`)을
안 고쳐 **하루 밀리는 회귀를 냈다.** 고치기 전엔 시각이 틀렸고 고친 뒤엔 날짜가 틀렸으니,
한 사이클 동안 오히려 나빠졌다.
→ 교훈: 저장 규약 변경은 **그 값을 읽는 모든 지점의 목록을 먼저 만들고** 시작한다.
  타임스탬프에서 날짜를 뽑는 일은 한 함수(`localDateKey`)로 모아, 호출부마다 UTC/로컬을
  다시 고르지 않게 한다.

## 기능을 만들 때 "그 기능에 도달하는 입구"도 함께 확인한다

2026-07-26, 실제 사용자 문장을 발화 라우터(`routeUtterance`)에 통과시켜 보니 **"줘"로 끝나지
않는 짧은 명령이 전부 rule(캔 답변)로 새고 있었다.** 그중에는 **Phase 19가 자기 명세에 적어둔
트리거 문장 "오늘 독서 했어"도 있었다** — 습관 체크 도구를 만들고, 승인 카드 라벨까지 붙이고,
api 6 tests로 잠갔는데, **입구에서 막혀 도구가 한 번도 불리지 않는 상태**였다.

같은 부류: "장보기 추가", "장보기 완료", "메모해", "페이지 만들어" 등 도구가 다 있는 동작들.

- 왜 안 잡혔나: 도구 테스트는 도구를 **직접** 호출한다. 라우터 테스트는 라우터만 본다.
  둘을 잇는 "사용자가 이렇게 말하면 이 도구가 불린다"를 아무도 확인하지 않았다.
- 왜 이렇게 됐나: 원래 `QUESTION_HINT`는 **질문** 힌트 목록이었다. Phase 10에서 명령을 살리려고
  "줘" 하나만 끼워 넣었고(그때의 실제 버그 대응), 나머지 명령 어휘는 그대로 빠져 있었다.
  **증상 하나를 고치면서 부류 전체를 보지 않은 것**이 재발로 이어졌다.
- 교훈:
  1. 기능을 추가할 때 **명세에 적은 예시 문장을 실제 진입 경로에 통과시켜** 본다.
     "이 문장이면 이 도구가 불린다"를 한 번은 확인한다.
  2. 분류기의 오분류 비용이 **비대칭**이면 그 방향으로 기운다. 여기선 잘못 llm으로 보내면
     무료 쿼터를 조금 쓰고, 잘못 rule로 보내면 **기능이 아예 동작하지 않는다.**
  3. 힌트 목록은 **도구 카탈로그의 어휘**로 좁힌다. 무작정 넓히면 인사까지 LLM으로 새서
     쿼터가 잡담에 소모된다(그건 GREETING이 먼저 걸러내게 두었다).
- 최초 발견: 2026-07-26 / 재발견 횟수: 1회 (Phase 10 "줘" 패치 → Phase 19 명세 문장 재발)
- 상태: active

## L-13. "규칙을 주석으로만 적어두면 다른 파일이 어긴다" — 랜딩 제목 브랜드 중복

- 분류: REF-HIGH (공개 진입점 노출 값 오류)
- 증상: 프로덕션 랜딩의 `<title>`이
  `Little Dev Duck — 오리가 사는 개인 워크스페이스 — Little Dev Duck` — 브랜드가 두 번.
  검색 결과·브라우저 탭·북마크에 그대로 노출되는 값이고, 랜딩은 유일한 공개 진입점이다.
- 원인: root layout이 `title.template: "%s — Little Dev Duck"`으로 브랜드를 자동으로 붙이는데
  `welcome/page.tsx`가 title에 브랜드를 또 넣었다.
- **핵심**: 같은 규칙이 `p/[slug]/page.tsx`에는 **주석으로 이미 적혀 있었다**
  ("직접 붙이면 브랜드가 두 번 나온다"). 즉 지식은 있었고, 지식을 적용한 파일도 있었다.
  **강제하는 장치가 없어서** 나중 파일이 같은 함정을 그대로 밟았다.
- 왜 안 잡혔나: 메타데이터는 타입체크·린트·유닛 테스트를 전부 통과한다(문자열일 뿐이다).
  아무도 **완성된 출력**을 본 적이 없었다.
- 교훈:
  1. 규칙을 주석으로만 남기지 말고 **검사로 만든다.** 주석은 그 파일을 읽는 사람에게만 닿는다.
  2. 검사는 **소스 파싱이 아니라 최종 출력**으로 한다. 여기선 `page.title()`로 브라우저가
     실제로 받는 값을 봤다 — 템플릿·상속·병합이 다 적용된 뒤의 값이라 파서보다 정확하고
     오탐이 없다.
  3. 타입·린트·유닛을 다 통과해도 **사용자가 보는 문자열**은 아무도 안 본 채로 배포될 수 있다.
- 최초 발견: 2026-07-26 / 재발견 횟수: 0회
- 상태: active (가드: `apps/web/e2e/public-visual.spec.ts`)

## L-14. e2e를 `playwright test` 단독으로 부르면 직전 빌드가 서빙된다

- 분류: 검증 신뢰성
- 증상: `welcome/page.tsx`의 메타데이터를 고치고 `npx playwright test`를 돌렸는데
  **옛 제목이 계속 나왔다.** 소스는 분명히 바뀐 상태였다.
- 원인: `playwright.config.ts`의 webServer가 `next start`, 즉 **미리 빌드된 결과물**을
  서빙하는 프로덕션 서버다(dev 서버가 아니라 hot reload가 없다). 빌드는 `pnpm e2e`
  (`next build && playwright test`)가 담당하는데 그걸 건너뛰었다.
- 위험한 점: 실패가 아니라 **조용한 거짓 통과**로도 나타난다 — 방금 깬 코드가 이전 빌드로
  green이 될 수 있다.
- 교훈: 앱 소스를 건드렸으면 e2e는 **반드시 `pnpm e2e`로** 돌린다. 스펙 파일만 고쳤을 땐
  단독 실행이 유효하다(스펙은 Next 빌드 산출물이 아니다).

## L-17. "없다"고 적은 실측이 사실은 "못 찾았다"였다 — velog 전체 피드

**재발견 1회**(1차 피드백 4-1 → 2차 피드백 4-1, 사용자가 같은 항목을 다시 올렸다).

**무슨 일**: 사용자가 `velog.io`를 등록했더니 0건이었다. 조사해서 "velog는 사이트 전체 피드를
제공하지 않는다"고 판단하고, 홈 주소는 **등록을 거부**하며 안내 문구만 띄우게 했다.
그리고 그걸 "완료"로 적었다. **2026-07-27 재실측: `https://v2.velog.io/rss/`가 200에 RSS 20건**
(전부 title·link·pubDate, 발행 시각도 당일)을 준다. **전체 피드는 있었다.**

**왜 틀렸나**: 1차 조사는 홈 HTML의 `<link rel=alternate>`만 봤다. 그건 "자동 발견이 안 된다"는
증거일 뿐인데 **"피드가 없다"는 결론으로 넘어갔다.** 없다는 것을 확인한 게 아니라 **못 찾은 것**이다.

**두 가지 교훈**
1. **부재 증명은 탐색 방법 하나로 성립하지 않는다.** "X가 없다"고 적으려면 어떤 방법으로 찾았고
   무엇을 확인하지 않았는지까지 적는다. 안 그러면 그 문장이 **다음 사람의 전제**가 된다
   (실제로 코드 주석·테스트·안내 문구 세 곳에 그 틀린 전제가 복사돼 있었다).
2. **거부는 해결이 아니다.** 안내 문구를 띄우는 것으로 "고쳤다"고 적으면 사용자는 같은 항목을
   다시 올린다 — 실제로 그렇게 됐다. 사용자를 **다음 단계로 데려가야** 끝난 것이다.

**가드**: `resolveFeedUrl`의 `unresolvable` 갈래에 "기본값으로 쓰지 말고, 데려갈 길이 정말
없는지 실측한 뒤에만 쓴다"를 계약으로 적었다. 지금 이 갈래를 쓰는 규칙은 **하나도 없다**(전수 확인).
